# SpeechNexus 军团工作流与职责

GitHub 保存产品需求、原始验收条件、代码审查和合并事实；Delegra / Paperclip 保存执行切片、依赖、工作区、产物和接收回执。产品进展以同版公开业务链和 AC 证据判断，任务数量、绿色 CI 和健康检查各自只证明覆盖范围。

**当前处于首轮产品切片交付阶段。** 用户已明确由唯一 SM+PO 直接派工推进上线，底座整改期结束；阶段事实以同版公开业务链和 AC 证据判断，不以任务数量或整改计划完成度判断。公开目录、任务提交/读取、同步 TTS、同步 ASR、制品下载均已合并且 CI 全绿，但**执行链路尚未接通**：同步语音入口在默认装配下返回 503（缺生产适配器），任务提交后没有消费者推进状态（[#254](https://github.com/hrygo/SpeechNexus/issues/254)）。当前关键路径是这两段接线，不是新增接口面。[闭环整改计划](../plans/2026-10-27-delegra-legion-closed-loop.md)与[旧环境报告](paperclip/environment-readiness.md)保留原时点事实。已移除的旧项目及任务编号不再承担当前队列、环境配置或门禁入口。

## 唯一决策方与执行结构

已登记的**唯一 SM+PO 会话**统一承担产品价值、优先级、迭代目标、范围、AC、执行排序及对用户的承诺，直接向适任成员派工；任务卡是唯一当期队列，岗位暂停或环境故障不改变阶段，只改变该切片的执行者。用户保留重大范围决定和最终 Gate / 投产放行权。

原产品总控会话转为按需独立架构 / 风险审查与备用接管，不保留第二产品队列；接管必须有新的明确安排。同一时刻只有一个 SM+PO。实际会话、平台对象、权限和环境入口由私有部署记录映射，公开源不使用“主聊天”或历史“经理”来猜测身份。此次基础设施整改的授权不自动扩成产品实施或投产放行。

首轮 [#30](https://github.com/hrygo/SpeechNexus/issues/30) / [#142](https://github.com/hrygo/SpeechNexus/issues/142) 的 TTS 硬上限切片另已有本用户 goal 的实施授权，持续有效；底座修复及所需岗位 / 资源准入后按该目标推进，无需再次确认。其他产品范围与投产放行不因此扩权。

现有七个平台注册岗位及模型 / 连接构成写前基线，不要求全员持续运行；当前授权允许根据逐岗验证调整 model / effort，记录理由、前值和回读。不得通过更换连接绕过预算或内容网络边界。平台组织树、职位名和 `leadAgentId` 不授予另一处产品决策权；外部会话不能伪装成平台 agent ID。公司级汇报关系变更须核对其他项目影响，不能为本项目简化而顺手改动。

## 一条执行队列与独立接收

GitHub [总控 #6](https://github.com/hrygo/SpeechNexus/issues/6)及原 issue 保留完整产品范围与 AC。唯一 SM+PO 在当前项目维护一条执行队列，只接入已批准目标的当期切片，不镜像创建全部长期工作包，不额外维护产品 backlog。计划和报告解释版本、依赖及证据，不成为第二份排序权威。

任务就绪前写清：

1. 已授权目标及决策来源、GitHub issue / AC、触发场景、预期结果和排除范围。
2. 实际完整 base SHA、目标分支、输入契约 / 制品版本，以及接收方可取得的输入。
3. 唯一写者与文件范围、适任非作者 reviewer、消费者和集成写者。
4. 实际执行主机、当前任务能力卡、准确环境入口、资源窗口、允许的运行态动作和禁止事项。
5. 按风险选择的验收、原始证据、失败退出条件与具名解阻方。

必要依赖在首次执行前进入平台门禁，并写出解除条件；父子关系、关联链接或整包未关闭不自动形成门禁。创建入口不能安全保存依赖 / 不执行状态时，先在现有队列保留候选，不先启动再补依赖。单个环境故障只阻塞受影响动作，无关独立项继续。

作者交付固定候选后，由非作者审查；指定集成写者取得并核验产物，按授权接入；QA 按风险验证最终候选；唯一 SM+PO 汇总专业结果并判断产品接收。常规切片不必调用集成助手。返修留在原切片，审查结果属于 reviewer 的报告，不改写作者原始证据。

- 普通局部改变由一名适任非作者审查，检查范围随风险选择，不要求七岗会签。
- 协议、原子事务、恢复、fencing、停止或预算释放等高风险改变保留非作者 Sol 审查及对应环境验证。通常 A 写 → B 审、B 写 → A 审；MiMo 第二视角按需选用。
- A/B 均参与实现时，保留独审缺口，明确委派未参与该候选的合格 Sol；可使用按需独立审查会话，不由作者换角色自签。SM+PO 不因负责调度而自动充当技术 reviewer。
- QA 验证最终候选的用户结果，不代替 Sol 代码审查；作者自测不能冒充独验。文档和低风险局部改变不固定占用完整 QA 窗口。
- 目标分支或补丁变化后，记录新候选及新增差异，只补验受影响的结论。旧 SHA 的审查不能直接放行不同字节。

## 三机路由、执行与制品

本机承担协调、主要开发 / 集成及适用 macOS 检查；MegaCube 承担 Linux aarch64、隔离数据库 / 对象存储与真实 GPU；MacBook 承担轻量独立消费者 / 浏览器验证。区分 agent 执行主机、被测服务和产品目标拓扑，不把三台开发机器视为已验的多 GPU 集群。

能力卡记录工具 / OS / 架构、可用服务、核验时间、资源类别 / 峰值、保留服务及当前余量。统一内存、常驻模型、KV、音频与测试峰值一起核算；GPU 利用率零、显存 N/A、标称内存和 swap 都不授予加载容量。本机共享推理、磁盘和浏览器，MacBook 一次一个轻量浏览器 / 设备窗口；重型 CPU 与 GPU 实验默认错峰。

任务明确 `SPEECHNEXUS_TOOLCHAIN_ENV` 的实际入口。执行者先激活环境，核对 `pwd`、完整 HEAD、工作区状态与版本，每个 checkout 安装自己的锁定依赖；缓存不等于当前依赖已安装，不链接其他 checkout 的 `.venv` 或 `node_modules`。仅加载该角色与切片所需规则、技能和验证范围，不强制所有岗位读完整管理手册或所有技能。

B / QA 保留现有 Legacy CLI 传输路径：历史 native SSH 空工作区和远端 commit 回收索引问题尚不能按名称统一或旧 hello 视为已修复。远端只回传工作区修改与报告，不 commit / push；新路径须另行取得实际 checkout、工具、产物往返和 finalize 证据。

交接至少包含完整 base SHA、完整 patch / 新文件、逐项 SHA-256 / 大小、输入版本、实际命令与原始结果、未验项和下一接收人。产物必须在获准存储可取得，接收方实际下载并核验，不能只交发送方本机路径。接入时同时记录来源 base / patch hash、目标 SHA、接入新增差异和最终候选 hash。原生 finish、修改回传、宿主接收与后置 finalize 分开判断；失败保留产物和恢复点，不重做语音业务或补造最终提交。

## 权限、预算与证据边界

保留关闭 timer、事件派工、单岗并发 1 及已有预算 / 价格准入保护；同时最多两个无写冲突开发切片，并受真实主机窗口约束。审查与文档也计入资源，队列约定不是 OS 硬锁。岗位恢复和任务启动由获准操作者按明确阶段执行，文档更新不自动解除暂停。

模型 ID、Harness、连接、实际思考级别及有效环境须逐岗核验，不能用 Harness 名称或模型后缀推断资格。Codex、Claude 和 OpenCode 的配置字段不能混用；具体核对矩阵见[整改计划](../plans/2026-10-27-delegra-legion-closed-loop.md)。任务分配、agent / skill 创建权限也须独立检查，模型连接成功不证明这些权限适当或工具链可用。

组织 skill 保存项目领域规则和可移植工作流；Harness 自带的系统技能由对应 Harness 管理，不成批复制进组织目录。确需跨 Harness 复用时，先核来源、版本、工具依赖和授权边界。平台原生运行控制由适配器提供；Native 控制面、Legacy 操作说明和 board 管理入口须分别匹配实际身份，工程岗不因载入管理技能取得管理权。

选中 skill 只提供指令，不安装工具或增加 MCP、浏览器、网络及写入权限。配置审查既看显式选择，也核最终投递的隐式运行技能；只读 / 离线岗位不应被要求主动发反馈、安装依赖或运行其没有的工具。风险限定和宿主已有证据规则适用于通用审查 / 验证流程，不把每次消息都变成全量新测试。

部署记录保存各岗选中 key、实际有效版本及正文 hash。未启用版本 pin 时，不能把填写 versionId 当作固定成功；首轮运行冻结版本、恢复复用原快照，也不等于不同新任务永远使用同一版本。实际准入时核运行快照与审定基线的差异。

model / effort 按当前授权和验证结果调整；不得通过改连接、额度、价格策略或共享服务绕过准入。历史费用更正不证明新运行免费或当前预算可用。配置 / 鉴权 / 工作区同因失败不循环重试，交具名成员排障；原因或输入改变并取得新证据后再运行。没有可推进工作时正常结束，不新建轮询、自动巡检或空转任务。

真实音频、转写、书稿、声音参考与业务派生内容留在部署网络和批准存储，不进入 agent 提示、外部模型、平台附件或 GitHub；验证使用合成或最小脱敏输入。凭据走批准的受管引用，能力卡和交接不复制秘密。保护既有模型、数据库与其他共享服务，不把本机共享库改作项目测试库。

证据分列契约 / fake、生产装配、隔离持久行为、公开真实引擎、浏览器 / 设备、物理多机及质量 / 许可 / 运维，标注版本、环境、通过 / 失败 / 跳过 / `not_run`。公开上传 → 实际音频 ready → 权威配置 / Job / 原子准入 → 真实执行 → 原身份发布 → SDK / 页面下载仍按原 AC 验收。首轮 TTS 硬上限候选及 GPU 回归不替代公开两链或 Gate。

## 角色源、部署映射与回退

[共同正文](paperclip/roles/common.md)与各岗聚焦正文是公开编译源；公司编排 skill 使用同一职责模型。私有部署 overlay 绑定唯一 SM+PO、独立审查会话、平台对象、实际环境与准入回执；它不能扩大源或任务授权。完整 runtime 正文由共同源、聚焦源和 overlay 编译，不要求公开角色文件与编译正文裸 hash 相同。

部署记录分别保存源提交 / 文件 hash、overlay revision / hash、编译规则版本和输出 hash。角色正文使用 `baseRevision` / hash，skill 使用 `expectedVersion` 实施受支持的 CAS；普通配置、model 和项目字段不支持 CAS，须串行写、保存写前值并回读验证，不声称原子更新。写前重读，发现并行变化时先核实意图，不覆盖未知修改。每岗正文应包含其必要共同边界，不依赖一次运行再去加载全部管理资料。私有身份、平台 UUID、机器私有路径和内部入口不写入公开源。

回退先停止本轮任务调度并保留运行 / 产物，再按记录恢复本次角色、skill 及项目配置。不重置 Git、不删除历史或产品数据，不自动恢复已失效的总控、旧队列或历史暂停。提交、PR、合并、发布及运行态变更分别按当前授权执行。

## 运行期规则与已踩的坑

以下规则来自实际执行事故，不是设计推演。每条都附当次可见后果，便于判断是否仍适用。

### 派工前先确认管道能跑

派真任务前先用一张一分钟的探针卡确认该岗能启动。2026-10-27 当天，某岗的 AI 账号在 16:02 被平台判定不可用（`ConfigurationIncompleteFailure`），随后两张真任务卡直接变成 `blocked`，其中一张在 20 分钟后才被发现完全没有产出。

### 单岗并发 1，建卡前先查 `in_progress`

同一岗位的第二张卡不会并发执行，只会排队，但界面仍显示 `in_progress`。当天因此出现"第二张卡看起来在跑、实际在等"的空转。建卡前查目标岗的在办卡数量，忙就等，不要靠卡片状态判断。

### 不要在已完成卡上补评论

给已完成任务补评论会唤醒该岗重新执行，产生一次无意义运行。验收结论写在卡片状态变更时一并提交，或写进 issue / 文档，不要事后追加。

### 时限按套件实际规模设，不按本机经验设

同一套 `tests/unit/gateway` 在本机数分钟跑完，在 Linux aarch64 执行机上 7 分钟仍未结束。跨主机任务卡应给出"单文件 + 明确分钟数"，或先 `--collect-only` 看规模，不要用本机速度估。

### 上游模型改名会被误判成鉴权失败

本地推理代理把上游已下架的模型名继续映射时，上游返回 `410 Gone`，平台侧把它归因为凭据失效，于是整个 AI 账号被标记为需要重新授权，全队停摆。代理侧 health 检查必须跑一次真实推理，模型别名保持稳定，只改到上游真实模型名的映射。

### 跳过不是通过

集成测试的 `skip` 不计入证据；`fake` 只证明覆盖范围；作者自测不得当作独立验收。独立验收要求不同主机、不同数据库大版本或不同取码路径，同一环境重跑不构成独立证据。

### 唤醒只有一个可靠方式：新建卡

改卡片状态、改指派人、事后补评论都不会触发派工。2026-10-27 当天，把 `paused` 岗改回 `idle`、把 `blocked` 卡改回 `todo`、把卡改派给空闲岗，三次都没有起来；而新建一张卡立刻进入 `in_progress`。

要让人干活就造新卡，不要指望改状态。旧卡随之作废，写清取代关系，别留两张同时可执行的同类卡。

### `paused` 是可改状态字段，不是不可变约束

当日五个岗长期停摆，被当成外部阻塞上报了两轮。实际上平台只是 `agents.status='paused'` 与 `lifecycle_state='paused'`，改回 `idle` / `ready` 即可恢复。遇到归类为"阻塞"的状态，先问一句"这个字段我能不能改"，再决定是否升级为需要他人决策的事项。

### `opencodePermissionMode=ask` 的岗无法无人值守运行

某个岗的适配器是 `opencode` + 模型 `paperclip/omlx-*` + `opencodePermissionMode: ask`，启动即失败，平台报 `original assignee is not invokable`。可用组合是 `codex` 适配器 + `codexPermissionMode: never`，与正常工作的岗对齐。改配置后仍不接单，因为唤醒只在建卡时发生（见上一条）。

### `maxTurnsPerRun` 决定单卡上限，大卡必然耗尽

同一岗的轮次预算是适配器配置项。当天一个岗在 60 轮上限下把预算全部用于探索，worktree 里零提交零改动，只在错误里留下 `error_max_turns`。跨多个模块的卡要么提高轮次上限，要么拆小；两者都不做就会安静地烧完。

### 检查点必须写"到点必须报"，不能写"卡住就报"

"卡住就报"是无效条款：卡住的岗不会认为自己卡住。同一批卡里，写了"第 30 分钟在卡里报一次进度"的岗准时报了进展与"没有卡住"；只写"卡住就报"的岗安静烧完 60 轮、零产出，四十分钟后才发现。

### 执行机只读检出时，按补丁交付并由集成方落地

有执行机的检出是只读的（`.git/index` 不可写、无 `gh`），永远开不了 PR。可行的交付方式是补丁 + 清单，由具备推送权限的一方落地：核对补丁 SHA-256 与执行机自报值一致、`git apply --check` 通过、逐文件与清单吻合、跑门禁与格式检查，再提交并说明哪些是集成方改的。当日据此落地的两个 PR 均一次全绿。

集成时**必须自己跑一遍格式检查**：执行机交付的 6 个新文件全部不合规，原样提交会直接挂在格式门禁上。这是集成方的责任，不是执行机的疏忽。

### 新增表或路由必须同步四类横切断言

以下断言在任何新增之后都会红，且都不在新增者自然会跑的测试里：路径全集（`tests/contract/test_asset_http_contract.py`、`test_operational_contract.py`）、数据库表全集（`tests/integration/test_coordination_foundation.py`）、迁移 head 字面量（现集中到 `tests/support/migrations.py` 的 `HEAD`）、授权列清单。当日一个新表就让六分片里的集成分片全红，而作者只跑了本卡测试文件。

派工时直接在卡面列出这四处，或要求跑一次相关集成分片。

### 两个并行 PR 会撞在同一个装配点

路由装配文件（`app.py`）是每个新切片的必经之处。当日两个 PR 各自基于旧主干，合并第一个后第二个立刻冲突。冲突通常两边都是新增，正确解法是**两边都保留**（两个 router 并存），而不是取一边；取一边不会立刻红，但会静默丢掉一个切片。合并前先看它与最近合并的 PR 是否触碰同一文件。

### 会话损坏时换新会话，不要修补

某岗的 native 会话在一次成功运行后损坏，报 `HarnessReconciliationError: persisted active turn ... is missing from thread/read`，此后新运行被拒（`New work must wait while a native run recovers its unfinished accounting`），卡片被反复置为 `blocked`，而该岗显示 `idle`。

处理顺序：清理卡住的 finalization 状态、清空该岗的历史 session id 强制新会话、**新建一张卡**（不是改旧卡状态）。修旧会话没有成功过。

### 单次运行有硬时限，且是**按岗可配**的

执行适配器配置里有 `timeoutSec`（`adapter_config.timeoutSec`，缺省不限）。某岗的实际值是 3600，一张"三处修复 + 全量测试"的卡跑到整数一小时被砍，报 `Timed out after 3600s`，**worktree 里 77 KB 改动一次都没提交**。

判断口径：**卡的规模要按"含环境搭建的整段耗时"估**，不是按"改几行代码"。新依赖、新 venv、模型下载都算在内。两种处理都可接受——把上限调大，或把卡拆小；什么都不做就会周期性丢掉一小时。

### 运行被砍后，先抢救工作区，再决定要不要重派

运行结束时工作区**不会被删除**，未提交的改动还在原处：

```bash
# 执行机上：导出已跟踪改动 + 未跟踪文件
cd <run_workspace>
git diff > /tmp/<run>.tracked.patch
tar cf - $(git status --porcelain | awk '/^\?\?/ && !/\.paperclip-runtime/ {print $2}') \
  | base64 -w0 > /tmp/<run>.untracked.b64
```

拉回本地后在**干净 worktree**（基于当前主干）上复原：

```bash
git worktree add /tmp/salvage -b <branch> origin/main
git apply --3way /tmp/<run>.tracked.patch
tar xf <decoded>.tar -C /tmp/salvage
```

然后**必须自己跑测试**：当日抢救回来的 ASR 实现有 9 个测试红，根因是运行层填 `"auto"`、域校验只认 BCP-47 的哨兵不一致——一次默认请求 100% 503。抢救不等于可用，抢救只等于"不必重做一遍"。

顺序上：**先抢救再决定**。直接重派会得到一个"已经做过一遍"的活，且新运行拿不到旧工作区的分支。

### CI 全绿不等于部署可用：按默认装配实测每个入口

当日 12 个 PR 全部 14/14 绿之后，用生产入口的默认装配（`create_app(settings=...)`，不注入任何服务）实测：

```
POST /v1/audio/speech         -> 503 backend_unavailable
POST /v1/audio/transcriptions -> 503 backend_unavailable
```

原因是这两个服务**只接受注入**，而 `create_app` 没有对应的 runtime 装配模块（其它服务如 `job_runtime` / `artifact_runtime` 都有）。同一轮还查出：`POST /v1/nexus/jobs` 只写 `speech_jobs` 一族，**不写任何派发意图**，网关也不读该表，`advance()` 在生产代码里零调用点——队列有生产者、没有消费者。

判据很简单，每次切片合并后做两件事：

1. **装配实测**：用默认 settings 建 app，逐个打新入口，记录状态码；503 要能解释成"确实缺配置"而不是"没人接线"。
2. **成对搜索**：新写一张表/一个队列，同时搜"谁读它"和"谁写它"。只有写没有读，就是没有消费者。

分层交付的固有盲区是：**每层测试只验证自己那层**，两层之间那段线没人写的时候，没有任何测试会红。

### SQL 字符串里的转义会变成真实字节

迁移 DDL 里写 `storage_version_id !~ '[\x00-\x1f\x7f]'`，Python 先把 `\x00` 变成真正的 NUL 字节；PostgreSQL 的 C 字符串在 NUL 处截断，报 `unterminated quoted string at or near "'["`，六个集成分片全在 setup 阶段失败。

改用 POSIX 字符类 `'[[:cntrl:]]'`（等价覆盖 0x00–0x1F 与 0x7F）。**单元测试发现不了这类问题**——正确性取决于"字符串里的字节是什么"，只有真实数据库解析才暴露。新增迁移一律在真实 PG 上跑一次 `alembic upgrade head` 再交。

### 并行分支的 diff 里会"删除"别人刚合并的东西

两个 agent 改同一片区域、先后合并时，晚提交的那个分支基线早于对方合并。rebase 到最新 `main` 后常常**没有文本冲突**，但 `git diff` 会把"我的分支里本来就没有那段新内容"呈现成**删除**。

实例：分支 base 是 `057fbfd`，`main` 已到 `1bcbf12`（新增了 ASR 结果字段与它的测试）。直接合并该分支会删掉 `test_vllm_asr.py` −96 行、`test_file_asr_result.py` −164 行——两个文件的改动都不属于这个分支的工作范围。

合并前必须做两件事：

```bash
git fetch origin main
git rebase origin/main
git diff --name-status origin/main HEAD | grep '^D'   # 每一行都要能解释
```

`^D` 里出现**本任务没打算删的文件**时，不要合，先问是谁的。rebase 成功后还要重跑受影响层的测试——冲突解决得干净不代表语义还在。

判据：**"能快进/无冲突"不等于"没有删除"。** 只有逐条看过删除项，才知道别人的成果还在不在。

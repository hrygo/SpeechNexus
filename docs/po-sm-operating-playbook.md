# 多 Agent 运行手册：用 Codex 会话与 subagents 持续交付

适用于由当前 Codex 会话统筹、按需派发 subagent 或委托 GPU Agent 的交付。补充[项目经理工作约定](project-manager-guide.md)与[交付 SOP](operations/agent-delivery-sop.md)，不扩大其授权范围；提交、合并、派工、改运行态的边界仍以根[工作约定](../AGENTS.md)为准。

当前产品范围以[总控 #336](https://github.com/hrygo/SpeechNexus/issues/336)及[完整矩阵](plans/delivery-tracking.md)为入口。本页用于推进已授权切片的交付、验收与恢复；空闲执行位置不构成派工理由。

## 0. 一句话版本

> 核对当前目标与输入 → 推进具名切片 → 固定产物并验收 → 收尾工作区 → 留下接续条件。

派工不是「发出去就算」：**以实际启动确认派工，以实际产物确认进展，以验收证据确认交付**。

## 1. 选择执行位置

| 位置 | 适用 | 不适用 |
| --- | --- | --- |
| 当前会话 | 需要频繁纠偏、与用户来回确认、跨文件小改动 | 需要长时间独占上下文或专用主机 |
| subagent | 独立定位、单一问题反证、文件范围清楚的实施、并行只读调查 | 需要与用户对话、需要多轮纠偏 |
| 宿主多路编排 | 同一问题拆成多个互不依赖的检查、批量审阅 | 有写冲突或结论互相依赖的任务 |
| Linux GPU Agent（Paperclip 通道） | 真实 GPU、Linux aarch64、隔离数据库 / 对象存储 | 本机可完成的工作；密集返修 |

未指派 subagent 的空闲不构成产能；派工前先看目标 issue、PR 和已占用的文件 / 工作区。GPU 通道是可选项，不是项目队列：任务卡只承载本次执行，AC 与交付始终在 GitHub issue / PR。

## 2. 委托 Linux GPU Agent（Paperclip 通道）

需要真实 GPU 或 Linux 隔离环境时使用；派发前确认输入可取得、通道可达、具名执行者与接收者、资源窗口。

```bash
scripts/dev-env/preflight-team-env.sh     # 通道可达与卡住状态，退出码 0 通过 / 1 有检查失败 / 2 配置缺失
scripts/dev-env/fleet-status.sh           # 只读面板；--json 供脚本消费
```

面板把执行位置分成几类：`有活没动`（空闲但名下有在办卡）、`可派活`、`超时`（running 超过阈值）、`唤醒异常`（近三小时存在晚于最近成功运行的 deferred / failed 唤醒）。`backlog` 与 `blocked` 是停放，不算该动没动。

| 面板标记 | 含义 | 动作 |
| --- | --- | --- |
| `有活没动` | 空闲，但名下有 `todo` / `in_progress` 卡 | 核对运行、排队、任务状态和唤醒记录，不能仅凭面板断定唤醒失败 |
| `可派活` | 空闲且无在办卡 | 仅在已授权切片输入就绪、无写冲突且资源允许时派工 |
| `超时` | `running` 超过面板阈值 | 核对进程、近期输出及产物；运行时间长不等于卡死 |
| `唤醒异常` | 近三小时有晚于最近成功运行的 deferred / failed 唤醒 | 查 `reason` 再处置 |

面板本身可能说谎：查询报错必须按退出码 2 处理，不能渲染成「无可执行事项」；未指派的 `in_review` 计数不按公司过滤；文本模式与 JSON 模式对暂停状态的退出码判断不同。迁移或改版后先用一个已知状态的任务做对照，再信汇总。

回执核对候选、命令、退出码和限制后落回 issue / PR；平台状态失败而产物已就绪时只处理状态，不重跑业务。同因权限、唤醒或路由失败保留诊断交通道维护者，不反复派发同一任务，也不把面板状态当作项目进展。

## 3. 派工简报

一段可复制的简报，最少包含：目标与 AC（或用户请求）、受检版本（base / SHA / 制品）、可写文件与唯一写者、期望产物形式（结论 / 补丁 / 报告 / PR）、审查与接收人、停止条件。缺项时先补，不靠执行者猜测；同一文件只给一名写者。

## 4. 并发与共享资源红线

- 同一文件、同一 worktree、同一引擎 / 端口不得两人同时写；撞车先核归属，不覆盖、不回退他人改动。
- 热点文件（门禁脚本、总入口文档、契约）指定唯一写者，其余人提需求。
- 项目合计最多两个无写冲突开发切片，同一写者一次只推进一个；subagent、多路编排与 GPU 通道共用这一额度。
- 派工前检查目标 issue、PR 和工作区是否已被占用；接管与派工前按[工作区收尾](operations/agent-delivery-sop.md#工作区生命周期与收尾)复核保留项，旧工作区处置未明确时不创建同一切片的新副本。

## 5. 观察与等待

- subagent 完成会主动通知；后台作业按作业结果等待。不轮询、不反复读取完整日志；需要状态时用有界查询并记录下一检查条件。
- 长任务在任务内约定与规模相称的检查点：已产生的候选 / 证据、剩余工作、阻塞，不只报告「仍在运行」。
- 同一工作没有新事实时不重复派发；相同原因失败先保存诊断再决定。
- 没有可用事件入口时，明确写出这个缺口，不新增常驻巡检或定时任务。

## 6. 失败模式与处置

| 现象 | 常见真因 | 处置 |
| --- | --- | --- |
| subagent 结论空泛、贴聊天记录 | 简报缺目标或版本 | 补目标、受检版本和期望产物后重派，不追加「再努力一点」 |
| 两个执行者改同一文件 | 派工时未划写入范围 | 停写、核归属、保留一方成果；改为串行或拆分文件 |
| 返回值与仓库不符 | 未取得实际 checkout 或版本漂移 | 以实际文件与 `git status` 核对，要求给出版本证据 |
| 重复劳动 | 未检查已占用的 issue / PR | 先检索原切片，复用已有候选与证据 |
| 审查不独立 | 审查者参与了实现或共享同一上下文 | 换独立会话 / 模型；同一会话换角色不算独立 |
| 执行超时或无响应 | 任务过大或依赖不可用 | 缩小范围、补输入后重派；保留已产生的中间产物 |
| 结果丢失 | 只存在会话输出中 | 结论与证据落到 issue / PR / 文件 |
| GPU 通道任务卡住 | 唤醒、暂停或路由问题 | 按上文面板状态核实；同因失败交通道维护者 |

原则：先核实执行状态和阻塞原因，再选择获准的恢复方式；保留已有成果，避免重复执行。

## 7. 用对照组诊断，不要猜

判断「这个执行位置坏了」之前，拿一个正常对象对照：比运行记录、配置和输入。曾有执行者被误改配置，回滚后证明原配置一直是好的，真正原因在外部连接。

没有对照组的「修复」很容易把好的改坏。

## 8. 任务切分：让每个任务都有可见产物

一条任务应提供可独立接收的产物、明确边界和必要证据：

- **验证缺陷**：逻辑修复用失败用例证明问题，再验证修复；纯文档按文档检查，不新增无收益测试。
- **回报关键变化**：固定候选、交接、实质阻塞和验收结论时更新原 issue，不按每个步骤刷评论。
- **说明阻塞**：给出缺少的输入、提供方与解除条件；继续同切片可独立完成的已授权工作，无工作可做时等待具体事件。
- **范围单一**：一个切片一个目标。范围宽的卡片容易长时间零改动。

判断任务是否卡住应结合进程或会话状态、近期输出、产物和等待的具体事件；运行时间或暂时没有新产物都不能单独证明卡住。

## 9. 文档与引用的机器判据

```bash
scripts/dev-env/check-doc-refs.py            # 检查可识别的「文件:行号」引用
scripts/dev-env/release-preflight.sh          # 历史候选的局部上线前检查
```

上线前检查默认会访问配置的网关，部分检查固定了历史候选的假设；执行前应阅读[检查项与证据边界](operations/release-preflight.md)，并对照目标部署。默认跳过的检查不代表通过。

最终验收应按具体候选及授权范围执行；仓库当前没有 `scripts/dev-env/final-acceptance.sh`。

`check-doc-refs.py` 仅识别脚本列出的文件扩展名与 `路径:行号` 格式，以 Git 跟踪的文件定位目标，并将行内标注「外部依赖」的引用排除在问题之外；它不检查普通 Markdown 链接，也不能证明目标行就是文档所说的内容。仍须检查其他引用并打开目标行核对语义。

## 10. 验收：门禁必须会红

- 新写或修改的门禁应使用已知不满足条件的反例，确认能检出问题；正常输入首次运行通过并不能证明门禁有效。
- 收紧判据时用反向对照：把被检查的东西退回修复前，门禁必须重新变红。
- 门禁说谎的两个方向都要防：说「绿」（漏报）和说「更差」（误报）——后者会让人去修不存在的问题。
- 文档说「已可用」、门禁说 FAIL 时，以门禁与实测为准，并改文档。

## 11. 等待接续时记录触发条件

任务尚未完成且需要等待时，记录恢复所需的具体条件，例如：

- 依赖的具体事件（哪个 issue 完成、哪个 PR 合并、哪个人裁决）；
- 已配置的周期检查（若有）；
- 需要人工决策的事项，写清所需授权、影响和建议。

没有可用触发机制时，明确写出这个缺口；任务已完成或没有后续工作时正常结束，不为续接创建巡检或定时任务。

## 12. 交接

用一页纸交接，包含：

- 当前目标与判定它完成的标准；
- 关键路径与主要交付缺口（按影响排序）；
- 每个执行位置的当前任务与下一项候选；
- 阻塞清单：解除条件、责任人、下一步动作；
- 本轮已合并的 commit 与仍未验证的结论（区分实测 / 文档 / 推断）；
- 工作区收尾：已清理 / 不适用；保留时列对象、具名负责人、原因、成果位置、解除条件与下次复核时间。

不写流水账。「谁在什么时候改了什么」不如「现在是什么状态、下一步谁做什么」。

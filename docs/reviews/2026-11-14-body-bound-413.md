## 核心结论：413 与 422 分码、边界值行为、分块传输

### 分码可区分且不重叠

两个上限各自独立、各归各码，实测无交叠：

| 触发原因 | 状态 | 稳定码 | retryable |
| --- | --- | --- | --- |
| 传输层收不下请求体（声明长度或实收字节 > `job_receive_max_bytes`） | 413 | `job_request_too_large` | false |
| 正文 `input.text` 超 4096 码点 | 422 | `unsupported_parameter` | false |
| 未知成员 / 坏 JSON / 非法幂等键 | 422 / 400 | `unsupported_parameter` / `invalid_job_request` | false |
| 负或重复 `Content-Length` | 400 | `invalid_job_request` | false |

优先级也正确：**接收层先于 schema 校验**。同一份带「未知成员（本应 422）」的正文，在
`max_bytes+1` 时得到的是 413 而非 422，证明 413 早于解析。

### 边界值是「包含上限」（inclusive）

`max_bytes = 262144`，正文取满 4096 码点，仅用非契约成员 `padding` 精确凑字节：

```text
  max-1 wire= 262143B -> status=422 code=unsupported_parameter   （越过字节上限，被 schema 拒）
  max   wire= 262144B -> status=422 code=unsupported_parameter   （恰好等于上限 → 通过）
  max+1 wire= 262145B -> status=413 code=job_request_too_large
```

更有力的一组：**完全 schema 合法的同一份文档**（`text` 4096 码点，仅尾部空白不同），
`≤ max_bytes` 时抵达准入（真实准入装配下 202，探针 fake 下 503），`> max_bytes` 时 413：

```text
admissible body wire = 12427 B; bound = 262144 B
   262143B (   -1) declared  -> 503 job_unavailable        （已通过接收层）
   262144B (   +0) declared  -> 503 job_unavailable        （恰好等于上限，通过）
   262145B (   +1) declared  -> 413 job_request_too_large
   266240B (+4096) declared  -> 413 job_request_too_large
```

所以 413 **不是「文档有错」的代理**：可被准入的文档仅因 wire 变大就会被 413。这与契约 description
中「独立于任何字段界」「部署配置决定」「不承诺固定字节数」的表述一致。

### 分块传输（无 `Content-Length`）：上限仍然生效

这是本卡最需要实测的一条，因为 `_receive` 只在**有** `Content-Length` 时做头部早拒，
无该头时依赖 `request.stream()` 的累计判断（`jobs.py:398-409`，`size > max_bytes` 即 `_TooLargeError`）。

先用裸 ASGI 驱动（精确控制 header 与分块），再用**真实 uvicorn + 真实 TCP** 复核：

```text
REAL uvicorn on 127.0.0.1:8099, job_receive_max_bytes=262144
  wire= 262143B (-1)  declared-length -> 422 unsupported_parameter  |  chunked(no CL) -> 422 unsupported_parameter
  wire= 262144B (+0)  declared-length -> 422 unsupported_parameter  |  chunked(no CL) -> 422 unsupported_parameter
  wire= 262145B (+1)  declared-length -> 413 job_request_too_large  |  chunked(no CL) -> 413 job_request_too_large
```

裸 ASGI 下以 8 KiB 分 33 片发送同一结论（`max-1`/`max` → 422，`max+1` → 413）。
补充变体：声明 `Content-Length: 0` 但实收 266240 B → 413（流式累计兜底，声明长度无法用于绕过）。

结论：**上限在分块传输下不失效，且边界同样 inclusive。**

## 十条逐条判定

### A. 契约声明可信度

**1. 「由部署配置决定、默认 256 KiB」是否会与实现漂移——可接受。**
表述没有承诺固定值：契约明写「It is a deployment setting rather than a contract constant;
the deployment default is 256 KiB」以及「the contract does not promise a fixed byte size」
（`contracts/speech-openapi.yaml:845-856`）。运维把 `job_receive_max_bytes` 改成 1 KiB–1 MiB
（`settings.py:174`，`ge=1, le=1048576`）时，「default 是 256 KiB」这句话仍然为真，因为它说的是
**默认值**而非实际值。另有一层防漂移：`test_the_declaration_names_a_deployment_bound_and_the_stable_code`
断言契约里出现的 `"<n> KiB"` 必须等于 `Settings.job_receive_max_bytes // 1024`，即**出厂默认值一改，
契约文本测试即红**。我实测把 `job_receive_max_bytes=1000` 后，413 边界随之移动到 1001，
契约文本仍写默认 256 KiB——两者不矛盾。
残余（不影响判定）：客户端无法在提交前得知实际上限，只能靠失败得知；契约没有提供可读的限额端点或
响应头。这是接口设计层面的最小信息缺口，不是漂移风险。

**2. 413 与 422 是否真可区分、不重叠——成立，边界已实测。** 见上「核心结论」：413 由字节、
422 由码点，两条路径互不吞并；`max_bytes` 恰好通过、`max_bytes+1` 才拒；4096 码点通过、4097 码点 422；
`max_bytes+1` 且带本应 422 的未知成员时答案仍是 413，证明接收层先于 schema。

**3. 新增 413 是否被 CI 静态检查覆盖——作者归因完全准确，且该类回归确实被挡住。**
删掉 `createJob` 的 413 声明后（变异 B）：

```text
  - undeclared_response_status: createJob can return 413; declared responses are 202,400,401,403,404,405,409,422,429,503
EXIT=1
```

同时 `CONTRACT_BASE_REF=origin/main make contracts-speech-changes` **仍是绿的**（exit 0）：

```text
HTTP structural baseline: cef394336929e4f520d11ebe962034ffc7dd02e2
Known HTTP structural checks: passed
  - ... HTTP serialization settings, added statuses/media and security scheme evolution
```

其 `UNVERIFIED` 元组（`scripts/dev-env/check-http-contract-changes.py:29-34`）明列
「added statuses/media」，故它不承担状态增删检测。而 `.github/workflows/ci.yml:298-299`
**无条件**执行 `make contracts-route-conformance`（不限 PR 事件），因此「handler 会返回 413 但契约
未声明」这一类回归确实被挡住——只要 CI 跑它。注意 `python3 scripts/dev-env/check-route-conformance.py`
在缺 `fastapi` 的系统解释器下 **exit 2 且 stderr 明示 could not run**（fail-closed，不是静默通过）；
Makefile 用 `uv run python`（`Makefile:86`），本次按 uv 运行得 exit 0。

### B. 错误映射与安全

**4. `declared < 0` 拆开是否正确——正确，且分块路径无上限缺口。**
`jobs.py:391-396` 把负长度重定向到 `ValueError("Invalid Content-Length")`，由 `except ValueError...`
返回 400。`_TooLargeError` 虽是 `ValueError` 子类，但其 `except` 子句在 `except ValueError` **之前**
（`jobs.py:456` 先于 `:463`），不会被误吞。实测：`CL=-1`、`CL=-262144`、`CL=abc`、重复 `CL` 全部 400
`invalid_job_request`。作者未测的两条变体：**分块传输无 `Content-Length` 的超大 body → 413**（见上），
**`Content-Length: 0` 但实收超大 body → 413**。故不存在「去掉 `Content-Length` 即绕过上限」的缺口。

**5. `terminal` 与白名单不含该码，两轴是否自洽——代码层自洽，用户层仍是死循环，但非本 PR 引入。**
两轴确为两个独立函数：处置表（`file-task-session.ts:70-85`，含新增
`[413, "job_request_too_large", "terminal"]`）决定**说给用户什么**；
`settlesReplayedIntent`（`:155-170`）决定**能否把持久意图判为已作废**。实测用户实际体验（探针会话）：

```text
[413] notice      = 提交被拒绝（413 job_request_too_large），但该拒绝不能证明原提交未执行；保留原键与未知状态，不要新建任务。
[413] unknown     = true  canReplay = true
[413] rejected    = undefined  canFinishTask = false
[413] after replay attempts = 2  createKeys = 8cb054a5-…,8cb054a5-…      （同一 key）
[413] after reload unknown  = true  canReplay = true  canFinishTask = false
[413] after reload notice   = 已找到原任务身份。请恢复读取；未确认的请求仅按原键重放。
[413] reload+replay attempts= 3  distinct key = 1
```

即：**notice 是「被拒绝」，但持久状态是 unknown，且不能放弃**。`canFinishTask` 要求
`!state.unknown`（`file-task-policy.ts:4-17`），所以渲染「准备新任务」按钮的条件
（`FileTaskPanel.tsx:249`）不成立 → 用户拿不到新幂等键 → 无法改用更小的正文重提；唯一被提供的
动作「按原键重放」会复述同一份超大 body，必然再次 413。用户处境比单纯「重试」更差：**文案明确
禁止新建任务，而重放不可能成功**。

三条限定，决定这条不升级为阻塞项：
- **非本 PR 引入**。改动前同样超限返回 400 `invalid_job_request`；我实测 400 走的是**完全同形**的
  状态（`unknown=true / canReplay=true / rejected=undefined / canFinishTask=false`，notice 除码外一致），
  因为 `rejectionDisposition` 对任意 4xx 都落到 `terminal`，而 `settlesReplayedIntent` 对非 409/422
  一律 false。故新增表项是**行为冗余的显式化**，不是新行为。
- **默认配置下工作台几乎不可达**：`TtsJobInput.text` 上限 4096 码点，`startText` 先本地校验，
  正常文档最大约 12–16 KB，远低于 262144 B；只有运维下调 `job_receive_max_bytes` 才可达——
  而这正是契约明写「a body accepted at one deployment can be refused at another」的场景。
- 作者**未声称**修好 #707 族；PR 的描述把这两个决定分开陈述，与实现一致。

判定：本卡**没有**修完 #707 那一族（对该码仍是卡住），但也没有把它弄坏，且理由（先于原键查找）
经代码验证为真（`public_jobs.py:608-613` 的原键重放确实在 `_submit_new` 之前，而 413 发生在
`submit` 调用之前）。建议按下方「建议修 3」另开一张后续卡。

**6. 是否把 413 误归 unknown——没有。独立复现变异 D：3 条红。**
把处置表改为 `"unknown-outcome"` 后：

```text
× 413 job_request_too_large is terminal
× does not let the body-bound refusal fall through to the unknown 5xx branch
× treats a body over the deployment receive bound as a refusal, not an unknown outcome
Tests  3 failed | 59 passed (62)
```

与作者陈述的「变异 4 会红、3 条」一致。会话级探针也确认 notice 走拒绝分支而非「提交结果未知」。

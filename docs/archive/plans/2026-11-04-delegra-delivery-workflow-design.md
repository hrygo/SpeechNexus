> 归档于 2026-11-07：本文记录的 Delegra 平台队列、状态与审核机制已退役；Paperclip 现仅作为 Linux GPU 委托执行通道，现行规则见[交付 SOP](../../operations/agent-delivery-sop.md)与[多 Agent 协作](../../operations/agent-collaboration.md)。以下保留 2026-11-04 的落地、试跑与阻塞事实。

日期：2026-11-04，Asia/Shanghai。状态：PR #410、#411 已合并并完成主干核验，七岗入口及相关 skill 已回读核对，#407、#408 的原有界 AC 已验收关闭；远端 QA 环境与两个临时目录仍有阻塞，见 §11.2。§11.1 保留合并前试跑事实。

## 1. 目标与设计判断

让每个已授权任务留下可接收、可持续维护的成果。代码任务应推进到可审查 PR，完成约定的评审与验证后交出待合并 PR；用户批准合并后继续完成主干核验与收尾。验证、调查和文档任务按其约定成果接收，不为了形式制造代码或 PR。

用户已授权必要代码提交、推送和创建 PR；合并仍须明确授权。PO 负责范围、排序、资源冲突、重大阻塞和接收，执行者负责日常实现、测试、返修、交付及工作区收尾。沿用一位 PO、每切片一位交付负责人、同文件一位写者、最多两个无冲突开发切片与单岗并发 1。

本方案的主要改变是：**将草稿 PR 提前到可运行候选出现时，把提交和 PR 变成执行路径的一部分；在派工前准备好运行条件、接收者和合法状态转换。** 独立评审和适用验证仍是转为待合并交付的条件，不能因提前建 PR 而省略。

本方案按用户明确授权修订现有 SOP、岗位与 skill；不改变运行权限、模型、预算或用户合并授权，不新增长期执行队列。

## 3. 选择执行方式

| 工作特点 | 默认方式 | 交付方式 |
| --- | --- | --- |
| 当前会话可快速闭环、反馈密集或环境仅在宿主可用 | 当前执行者直接完成 | 按授权提交/PR，或直接交出用户要求的结果 |
| 一次性、可独立的定位、反证和审查 | subagent | 返回结论、依据、受检版本和限制，不必另建持久卡 |
| 需要跨会话持续执行、专用主机/数据库/GPU、正式回传 | Delegra 原切片任务 | 一位交付负责人贯穿实现、返修、PR 与收尾 |

不按 Agent 是否空闲派工，不把实施、自测、打包、PR 各拆成一张卡。独立验收确有不同环境或责任边界时才拆子任务，并复用原切片的输入、版本和接收约定。不同机制合计受同一并发与资源限制。

## 4. 两种代码交付路径

### 4.1 可直接提交的执行环境

具备已授权的取码、commit、push 和 PR 能力时：

`实施与回归测试 → 针对性检查 → commit/push → 草稿 PR → 独审与适用 CI/验收并行 → 原 PR 返修 → 待合并 PR → 接收 → 获准合并及收尾`

本地提交可作为保存点；出现有意义、可审查且通过适用基础检查的增量后推送并建立草稿 PR。无需等真实引擎、完整运行资格或全部业务 AC 才允许建立草稿。失败和未验内容明确写在草稿中，不能以草稿存在宣称交付完成。

### 4.2 只能回传修改的执行环境

既有远端 adapter 无 Git 发布能力或现行部署要求只回传时：

`远端实施与测试 → 平台原生回传 → 具名集成写者核验并 commit/push/建 PR → 同一个 PR 审查和返修`

集成写者在派工时指定，且预留接收能力；可以是作者对应宿主操作者或按需集成助手，不默认全部交给 PO。复用现有工作区、原 run 与回传机制。先核验回传/finalize 和写入交接，避免作者与接收者同时写同一位置。

只有传输边界确实需要时才交完整 patch、新文件及 manifest。已在远端 PR 保存的同版代码，正常以完整 commit SHA 为候选身份，不再要求每个角色重新打包一份代码 ZIP。私有附件访问必须实测；必要时向指定审查卡提供同一制品，不靠放宽权限解决。

### 4.3 三类交付结论

| 类型 | 可接受的阶段交付 | 不构成完成 |
| --- | --- | --- |
| 代码任务 | 精确 head 的非草稿 PR、适用检查和独审完成、接收人已确认、收尾已处理或登记例外 | 只在本地改好、只上传 patch、只建草稿、只自测或报告 done |
| 验证/调查任务 | 接收人取得报告和必要原件，核对版本、命令、退出码、限制并记录接收 | 空输出无退出记录、不可取得的私有路径、运行成功但无业务结论 |
| 文档任务 | 按授权交出已接收的文档；维护仓库有效文档时走适用 PR 流程 | 只在聊天承诺更新、把设计建议当成生效规则 |

Delegra 可在约定的“待合并技术交付已接收”阶段结束执行；GitHub issue 保持开放，直到主干包含成果且完整范围与 AC 满足。若任务授权本来包含合并后收尾，则相应阶段仍由原负责人承担。合并等待本身不要求作者保持活跃，也不强制保留整棵工作区。

## 5. 就绪检查：准备好再唤醒

沿用现有任务正文，用六项最小信息完成派工，不新增复杂表单：

1. **结果**：issue/AC、写入范围、任务类型及终点；代码终点默认是待合并 PR，而不是候选包。
2. **版本**：完整 base、目标分支、已有 PR、固定输入及来源，先去重。
3. **责任**：交付负责人、唯一写者、适任非作者 reviewer、接收者；回传路径另列集成写者。角色可由同一人兼任，作者不能兼任其独立 reviewer。
4. **环境**：实际 adapter/主机/身份、独立依赖和相关缓存可写、必要命令能启动、服务归属、资源窗口、证据往返可用。
5. **授权**：按动作明确 commit/push/建 PR、隔离测试和运行边界；现有用户授权不重复询问。合并、部署等另按各自授权执行。
6. **接收**：受检版本、必要检查、原件位置、平台认可的审核/阻塞/完成路径，以及失败时具名受理者。

能力验证在最终执行身份中进行；不是只测宿主二进制存在或模型能回答。对普通 Python 开发，至少验证锁定环境和缓存的必要访问、测试/检查入口及回传；需要 nginx、容器或数据库时再增加对应动作。使用合成输入，不接触生产服务，不因预检增加整套业务测试。

同 adapter、工具链、依赖与相关策略未变，且无相关失败时复用能力回执；失败后只重验受影响项。服务容量和独占窗口在实际使用时确认。环境存在缺口时，可继续独立实现，但必须把缺口、接收操作者和补验窗口事先明确，不能将全部交付责任留空。

## 6. 实现、审查和验收

- 作者拥有实现、回归测试、必要文档和修复的完整切片范围。安全修复和长期行为必须有随 PR 保存的有效回归，不能只留临时脚本。检查按[验证指南](../../agent-verification.md)选取，避免无关全库检查。
- 草稿 PR 出现后，静态独审与可并行的 CI/验证同时开展；依赖具体运行结果的判断等其证据，不用阶段标签替代输入。
- Reviewer 与接收路线由 PO 在派工时预先指定。作者提交候选后只触发既定接续，不自行选择新 reviewer、另建产品任务或增加资源额度；平台能否自动接续须先实测，未验证时由具名操作者执行同一安排。
- 每个审查结论固定精确 head 或可核验补丁身份。普通切片一位适任非作者即可；协议、协调事务、恢复、fencing、停止及预算释放保留非作者 Sol 和对应环境验证。平台 `not_creator` 不能替代“未参与代码实现”的核实。
- 返修沿原卡、原分支、原 PR；作者更新最终候选，reviewer 复查变化与受影响结论。变更涉及执行入口、TLS、模板、配置校验等时，应补验相关装配；不机械重跑无关检查。
- QA 按原 AC 和风险验证最终候选。只有需要不同主机、数据库、取码路径等独立性时，才占独立验收窗口。角色名变更不形成环境独立性。
- 某项真实引擎、物理拓扑或镜像资格不在当前 issue 范围时，列为产品未覆盖事实，不能无依据扩大成本。属于当前 AC 的前置缺失则保持未满足，草稿可保全成果，不能把范围裁掉以求完成。
- 转为待合并 PR 前，确认无未处理的阻断发现，检查与受检版本一致，必要 AC 证据已齐，PR 正文反映最终实现；仍需额外验收时用普通 issue 引用，避免合并自动误关。以[贡献指南](../../../CONTRIBUTING.md)的关闭语义为准。

## 7. Delegra 状态和接收机制

保留现有状态名称，不新增一套状态标签。GitHub 保存 AC、PR 和合并事实；Delegra 保存执行和接收；需求矩阵由现有机制关联，不复制成另一份人工状态表。

| Delegra 状态 | 必须表达的事实 | 下一责任人 |
| --- | --- | --- |
| `backlog` | 输入或窗口尚未就绪，尚未启动 | PO/明确提供方 |
| `todo` | 必要输入、授权、执行和接收路径齐备 | 原执行者 |
| `in_progress` | 有正在进行的实质工作或有据可查的运行 | 原执行者 |
| `in_review` | 固定产物可取得，平台认可的 reviewer/接收请求有效，责任人明确 | 指定 reviewer/接收者 |
| `blocked` | 必要动作缺条件，具名 owner、下一动作和解除事件明确 | 解阻者；不把同因重试交回无权限作者 |
| `done` | 约定阶段成果已被接收，代码有对应 PR，收尾已处理或明确例外 | 原负责人承担明确剩余交付责任；PO 保留产品接收权 |

### 7.1 先配置合法审核路径

核验时，Paperclip OpenAPI 声明支持 `executionPolicy.stages` 的 review participants、`reviewRequest`、定向 interactions 及 resolver policy。目标应是**原任务上直接指向适任接收者**，而不是反复新建审查卡后再尝试强设 `in_review`。

这些字段在契约中存在，不等于当前连接器提供它们，也不证明当前身份与 adapter 已端到端通过。当前 MCP 更新工具只覆盖部分字段，普通 CLI update 也未暴露全部策略；落地时使用已授权且支持该参数的官方入口，不能把未声明参数拼进 MCP 或宣称已配置。

优先验证原生 review participant 路径；若原生流程无法满足模型/环境隔离，再用子审查任务，并确保源卡存在被平台认可的接收/阻塞目标。验收包括：reviewer 可读取精确候选、只唤醒该 reviewer、结束作者 run 不触发无目标等待、结果能交回原作者、接受后能合法终止本阶段。

首次只在获准测试范围验证这条路径。尚未验证前，由具名 board 操作者在原卡承接状态处置，使用正式 `blocked` 与 `unblockDescriptor` 记录明确动作；不把“另有子卡”假定为审核成功，也不靠 `done` 消除警报。

### 7.2 安全启动和幂等

1. 在 `backlog` 准备原卡的输入、附件、责任和依赖，再配置接收路径；避免创建即运行后补材料。
2. 回读并核验就绪，最后一次操作才提升到 `todo`。当前 OpenAPI 声明此提升可只携带 `status=todo` 与原 `expectedStatusVersion` 作条件更新；该保护不覆盖全部字段或全局资源，须使用实际支持的入口并先试验。
3. 409 时回读并协调，422 时修正字段/流程，403 时交有权限操作者；不换身份绕过。创建、状态更新、评论、push 或建 PR 结果未知时先查询原对象，再补缺失动作。
4. 保留一个操作身份/请求 ID 重试同一写入；不为一次不确定结果制造另一张卡、另一个 PR 或重复执行。没有幂等能力的入口依靠事前去重、写后查询和串行操作，不声称原子性。

### 7.3 恢复先分类

| 类型 | 处置 |
| --- | --- |
| 产品失败 | 作者沿原候选修复、补回归及受影响验证 |
| 环境/权限失败 | 保存候选和精确故障，交环境/平台操作者；执行者继续独立工作，无独立动作则带 owner/条件阻塞 |
| 产物已完成、状态失败 | 接收者先验原件；已满足阶段终点则正式接收并结束阶段，否则建立具体审核或阻塞目标。仅修状态，不重跑产品工作 |
| 外部操作结果未知 | 按原身份查询远端、run 与回传，不重做提交/发布或重启未知执行 |
| 普通暂时网络错误 | 有界重试；写入先核结果，相关原因未改变不重复唤醒 |

同一权限/状态原因出现一次即保存诊断交具名受理者；只有权限、环境、输入或请求得到实际修正后才重试。同因第三次仍升级给同一个 board 不算恢复进展。不得通过清 session、改预算、伪造停止证据、强行改成功或重复执行消除状态问题。

## 8. 交付证明与版本复用

正常代码交付只维护一个最小接收记录，放在原卡/PR 的现有正文或文档中，不新增独立状态数据库：

```text
交付物：PR URL + 完整 head SHA；或任务原生附件 ID + 摘要
接收者与结论：已取得 / 已核验 / 已接收；范围为技术阶段或完整 AC
验证：命令、环境、输入版本、退出码、结果原件及适用范围
审查：reviewer、受检 SHA、发现与处置
剩余：未验项、owner、下一动作与解除事件
收尾：已清理 / 不适用 / 具名保留例外及下次复核时间
```

空日志必须保存命令与退出记录；失败、跳过及未运行分别列出。代码身份可用完整 SHA，跨环境非 Git 制品按需保留大小/摘要清单；平台附件可取得后才交接。只有有权、确需接收的角色取得材料，真实内容、凭据、私钥和无关主机信息不进入公开 PR。

验证复用看相关源码/制品、输入、工具/环境与检查配置是否相同，以及证据是否覆盖所需结论。单纯 commit 元数据改变不必重跑相同字节的检查；受影响字节或环境改变则补验。CI 以新的候选执行时保留新结果，不将旧版本的绿灯直接套用。

宿主模拟、schema/fake、生产装配、隔离持久行为、真实引擎、正式消费者和物理拓扑各自限定范围；先保全 PR 不等于放行部署。

## 9. 完成后的交付保障

- **成果保全**：代码推到授权远端分支并实际核对 SHA/PR；不能推送时交可下载、可恢复且包含新文件的正式制品，并指定集成写者。未提交文件不能只留在一台机器。
- **接收闭环**：作者交出证据后由预定接收者核验，不能仅以作者自报结束。普通代码的必要自测与独审无阻断后交待合并 PR；只完成草稿则仍有明确负责人。
- **合并闭环**：接收者把精确 PR head、检查、剩余限制和授权范围汇总供用户决定；已有合并授权直接执行，无授权才提交具体可评审对象。获准后沿原切片合并并核验远端主干包含实际成果、必要合后检查及 issue/矩阵同步。
- **资源闭环**：按现有[工作区收尾](../../operations/agent-delivery-sop.md#工作区生命周期与收尾)确认原执行、回传和相关进程停止，保全独有内容后清理。文件 finalize、平台绑定、Git 与物理目录分别核实，业务/费用未知不伪造成已结清。
- **保留例外**：无法同轮清理时，在原任务写对象、具名负责人、原因、成果位置、解除条件和 24 小时内复核时间；超期由现有巡检员通知，不自动续期或强删。

一个任务完成后不再为例行状态评论唤醒作者。后续合并授权、返修和实际缺口是合法接续事件。PO 每轮处理完派工和问题后按用户要求等待巡检通知；没有有效 Goal 时不自动创建 Goal。

## 10. 巡检事件与有限自动化

沿用现有巡检员，PO 不监控军团面板。巡检按有意义变化通知：

| 事件 | 通知对象与动作 |
| --- | --- |
| 候选已可评审 | 指定 reviewer 取得输入；只有接续链失败才交 PO |
| 必要验证/复审完成、PR 可接收或待合并授权 | 原交付负责人及 PO 推进下一步 |
| 环境或平台错误、无人负责的等待 | 具名解阻者处理，PO 协调资源/决策 |
| done 无约定成果、PR head 与审查/证据不一致 | PO 核实并恢复真实交付阶段，保全成果 |
| 清理失败或保留例外到期 | 原交付负责人/具名操作者处理 |

同一任务、候选版本、原因及处置状态形成同一事件；无变化不重复通知或唤醒。变化事件的去重属于待实现行为，不假定现有巡检脚本已经支持。停用或不可用的通知机制须有明确 board 受理者，不能以计划中的事件订阅支撑当前等待。

可选自动化仅做预检、条件启动、收集命令退出记录、校验交付链接及形成接收草稿；不自动替人签审查、不扩大权限、不据测试通过自动合并或关闭产品 issue。优先组合现有平台原生能力，确认接口缺口后才补工具。

## 11. 分步落地与验证

以下顺序已获用户批准。本次复用 DEL-469 / PR #410 和 DEL-470，不新建产品或审查任务。

1. **对齐现有规则。** 收敛修改交付 SOP、岗位 common 和实际投递的角色/skill 快照，明确直接提交与远端回传两条路径、代码终点和接收责任。历史证据保留；不重复拷贝全文、不增设第二 PO 或队列。实际部署逐项核验来源和有效版本。
2. **验证一条平台交接链。** 对当前身份/adapter 试验 backlog 准备、条件提升、产物绑定、定向 review、拒绝返修、接受结束与阻塞恢复。模拟缺 reviewer、附件不可读、权限拒绝、重复通知及结果未知，确认均不会触发同因无限重跑。不能只验证 schema 接受字段。
3. **试行少量真实切片。** 选择输入就绪的普通代码切片和只读 QA 各一项，已在办的优先；使用下一交付技能选择新产品切片，但不为试验预铺 backlog。高风险切片保留全部既定门禁。
4. **按结果扩展。** 复盘实际周转时间与重复执行，只有路由和接收均稳定后再扩大；平台交接有问题时退回明确 board 受理与原生制品保全，不重新执行已完成工作。

试行必须证明：

- 所有已接收代码阶段都有远端待合并 PR、精确候选、适用审查与验证；所有已完成 QA 都有可取得、带退出结果的原件及接收结论。
- 草稿出现后沿原 PR 返修，持续性回归进入仓库；无“本地完成但无人提交”的无主成果。
- 作者、reviewer、接收者真实可达，三方不会同时写同一文件；任务结束后没有无目标的 `in_progress` 或 `in_review`。
- 同一未修复权限/状态错误不会因自动恢复再次运行产品工作；只处理发生变化的事件。
- 相关停止、回传、finalize、清理与例外事实可核验；保留用户和其他任务改动。
- 按已有时间戳统计“就绪→首个草稿 PR”“首个草稿→待合并接收”“接收→合并/主干核验”，另记阻塞时长、同因重试、人工搬运和未推送成果数。未知数据留空；初期小样本用于改进，不宣称统计优势，也不新增常驻统计任务。

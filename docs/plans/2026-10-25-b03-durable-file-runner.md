# 文件 ASR 持久执行接线

承接 #142、#152 和 #154。目标是让原提交入口驱动文件处理并登记固定结果，
而非在调用方手工调用媒体组件。公开 Job、A 发布和 SDK/C 下载仍按原阶段要求推进。

## 唯一执行资格与短握手

原 `create_submit` 的唯一 INSERT 是新执行的唯一来源；原提交服务继续负责完整请求、
入口屏障和接收观察。文件执行适配器的短握手只核验原请求并准备本进程的接收身份，
不读取对象、不解码、不推理，也不创建第二份持久任务。

提交服务仅在新 intent 的接收观察已确认提交、且已退出入口锁后，调用执行启动端口。
普通引擎适配器不要求该端口；文件适配器显式配置它。回调不能用于已存在 intent 的重放、
查询或恢复。失败时丢弃尚未启动的本地准备项；这只回收本地内存，不修改容量预算。
启动错误沿原身份报告未知，不能撤销已提交事实或重新调用 dispatch。

文件适配器核对数据库原身份、摘要、接收 ID 与版本，只启动自己的准备项一次。
本地准备项和正在运行的协程用于执行与取消，不作为集群幂等权威；不同消费者仍由原
唯一 INSERT 和版本事务串行。长处理、对象 I/O 和推理都在提交事务及入口锁之外。

## 内部端口与兼容边界

`CommittedExecutionStarter.start(intent)` 只接收本次新接收且已确认提交的完整 intent；
适配器核对原身份、请求摘要、接收 ID 和接收时间。已启动的本地准备项不重复启动，
不存在对应准备项时返回结果未知，不能依据数据库中的 executing 记录补建执行。
`discard(submit_intent_id)` 仅丢弃尚未启动的本地准备项，不关闭执行、不归还预算。

`FileExecutionLedger.check_file_start(intent)` 在实际处理前使用既有锁序重检版本、
原身份、租约、实例代次、屏障与期限；读检查本身不授予所有权，也不创建第二次认领。
`list_unfinished` 是有界且按 gateway/node 隔离的启动枚举，只服务未知隔离。
接收提交到启动回调之间若进程退出，恢复沿原身份隔离，不能把该窗口变为重复外发入口。

已有提交服务的启动端口缺省为 `None`，普通引擎调用方不改变原行为。
新能力通过 `create_app(file_execution_factory=...)` 显式装配，不增加公开或内部 HTTP
字段、协调写端口、表或迁移；依赖 #152 的原回执事务和 #154 的有界异步输入。
未配置真实引擎时仍不可对外声明真实 ASR 就绪。

## 结果、取消与崩溃

- 原命令消费者运行一次，私有结果仅 staging 一次；完整回执经原观察事务登记。
  登记确认丢失只查原记录，已有完全相同回执可恢复，不能重新推理或 PUT。
- 取消使本地处理退出；记录和资源继续按原 unknown/可信停止流程协调。
  本地 task 结束、网络关闭和结果 EOF 均不签发 GPU 停止或释放事实。
- 启动恢复先枚举本 gateway/node 的未终结记录，将原进程遗留的活动执行隔离为 unknown；
  已有回执保留。恢复不启动这些记录、不读取可变默认、不创建替代执行。
- 真实停止仍由可信节点来源及原 `record_stop` 处理，A 原事务唯一决定预算归还。
  整实例停止必须覆盖该代次全部执行，不能把单个文件完成外推为共享实例可释放。

## 生命周期与失败清理

组合根在控制面构建、工厂调用和后台启动的线程完成后才传播取消；重复取消也不能
提前关闭仍在使用的连接池或入口所有权。退出先停止文件处理并等待数据库写入完成，
再关闭恢复 worker、连接池和进程入口。等待失败时保留权威资源，不报告清理完成。

线程尚未创建就启动失败时，没有后台写入需要等待；不得对未启动线程调用 join，
否则清理会再次失败并阻止释放未使用的控制资源。线程已启动但迟到时仍须实际等待，
超时不能假装已经退出。关闭过的 runtime 不得重新启用。

## 装配与验收

由组合根显式装配后台生命周期、提交后启动端口、原 ledger 和文件处理端口；
默认未配置时保持不可用。应用/领域不导入 HTTPX、MinIO、FastAPI 或 vendor DTO；
基础设施不导入同层的 interfaces。公开协议和 18 个协调写端口不增加。

验收覆盖：提交后才执行且不占入口锁；原键重放与两个消费者竞争只启动一次；
接收提交丢确认零执行；结果登记丢确认不二次推理/写对象；取消/期限保持未知；
重启原身份恢复且不重跑；真实隔离 PG/MinIO/HTTP 接线与固定回执恢复。
确定性用例使用合成识别/VAD，不能据此宣称真实模型或业务链资格完成。
后续使用固定 binding/版本/许可和批准引擎取证，再与 A/C 同版联合验收。

两个独立消费者的隔离 PG/InnoDB 用例使用同一合法进程入口、独立 ledger 和执行器：
两方先同时读到原 intent 不存在，再观察实际入口锁竞争，并分别验证两方先取得入口的情况。
每次只有一个新接收/一次文件处理，另一个返回原身份；结果版本与持久回执一致。
对象检查递归列举实际版本，不以目录项数量证明 PUT 次数。
这不是两个进程同时持有同一 gateway 身份，也不是物理集群证据。

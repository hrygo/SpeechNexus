# 团队 C 下一阶段 Goal：交付基线集成与真实业务闭环验收

> 执行者按本文件逐任务推进，任务勾选与 AC 勾选分开维护。代码实施按当前授权和适用的 `executing-plans` 技能执行；本文件定义阶段目标与验收路径，不替代机器契约或尚未冻结接口的实施设计。

**Goal：**在固定的共同集成 SHA 上，交付可部署、可恢复、可复验的 C 应用基线，补齐 C 可独立完成的功能与体验缺口；优先完成真实文件转写和文本配音两条基础闭环，再按具名制品接入音色、有声书、实时与助手，最终满足 C00–C08 原有范围及目标部署资格。

**架构：**沿用工作台独立领域、应用、持久化与对象区边界，通过公开语音协议消费底座。以契约和生成类型连接生产服务、正式页面及测试；合成回归、真实服务、真实模型、物理设备和目标拓扑分别取证。

**技术基线：**既有 Python/FastAPI、PostgreSQL、MinIO、TypeScript/React、生成契约客户端与浏览器测试链。具体版本按仓库锁文件，不做无关升级或重构。

**范围依据：**[三团队交付计划](2026-10-23-three-team-delivery-plan.md)、[C00–C08 持续目标](2026-10-24-team-c-goal.md)、[契约索引](../../contracts/README.md)和 [PROGRAM #6](https://github.com/hrygo/SpeechNexus/issues/6)。本文替代上一版 G-C1–G-C5 的推进排序与验收表达，不缩减原工作包或 Gate 的范围。

现状判断调整为：**C 已交付大量可追溯的应用切片；下一阶段同时存在集成风险、C 自有功能缺口、外部具名依赖及真实资格缺口。必须分别解决，不能只做“体验与证据收尾”。**

1. 保留证据分层、原键恢复、显式发布、诚实状态和失败诊断；测试数量与文件数量不作为完成率。
2. 先收敛共同基线，避免在旧分支上反复补证。A/B 整包未完成不代表全部接口不可用，应逐项核对已交付制品。
3. 契约覆盖按操作集合及映射判断，不要求操作数、绑定数、组件数相等；一个消费者可调用多个操作。
4. 下载/SSE 协议验证可以使用真实服务和合成内容，不必等待 GPU；引擎生成、声音复用和质量资格仍须另外取得真实证据。
5. “某按钮在另一流程通过”不能排除当前场景的产品缺陷。未解释的失败保留原因未定状态，不先定性为陈旧探针。

## 三、执行边界与重点风险

- 保留用户数据、现有未提交改动和其他任务成果；同一位置出现来源不明的并行修改时暂停该处写入并核对，不回退或整文件覆盖。
- 本文和原生 Goal 不扩大授权。提交、push、合并、发布、删除真实数据、跨 chat 发消息、模型下载/加载和外部运行态变更仍按当前用户授权执行；未获授权时先完成可评审制品与隔离验证，不以文档代替授权。
- 保持无登录/RBAC/多租户的共享部署边界；工作台不导入 speech 内部、不共写底座表，底座可在工作台和 LLM 关闭时独立运行。
- PostgreSQL 是正式权威库；MySQL 仅提供约定协调路径的可移植性证据。模型、运行数据、凭据及 `.runtime/` 不入库。
- 内容及派生内容不离开部署网络；LLM 默认关闭，仅消费服务端批准的本机/内网端点，无公有云回退。客户端不能指定任意服务地址。
- 不手改生成产物、不绕过准入、不以 HTTP 取消代替远端停止；旧 generation、结果未知和资源未释放各自保留事实。

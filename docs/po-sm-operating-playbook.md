# PO / SM 运行手册：怎么带一支 Agent 团队持续交付

适用于**由多个 Agent 组成、通过任务卡与巡检脚本协作**的交付团队。补充[项目经理工作约定](project-manager-guide.md)，不扩大其授权范围；可提交、合并、派工、改运行态的边界仍以根[工作约定](../AGENTS.md)为准。

本页回答一个问题：**PO/SM 每轮到底该做什么，才能让团队一直有活在干、有成果在验收、卡住的能恢复。**

## 0. 一句话版本

> 跑面板 → 看谁空、谁卡、谁等我 → 补齐任务 → 落实派工 → 核验真启动 → 留好下次触发。

派工不是"发出去就算"，**以实际启动确认派工，以实际产物确认进展，以验收证据确认交付**。

## 1. 每轮第一步：跑面板，不要回忆

```bash
scripts/dev-env/fleet-status.sh          # 人看
scripts/dev-env/fleet-status.sh --json   # 脚本/CI 消费
```

退出码 `0` 无事项 / `1` 有事要动 / `2` 面板不可用或调用无效（如缺 `psql`、连接或查询失败、多公司未指定 `--company`、无效的 `--watch` 值或未知参数）。

面板把 Agent 分成可操作的几类：

| 面板标记 | 含义 | 动作 |
|---|---|---|
| `有活没动` | 空闲，但名下有 `todo`/`in_progress` 卡 | 核对运行、排队、任务状态和唤醒记录，不能仅凭面板断定唤醒失败 |
| `可派活` | 空闲且无在办卡 | 这是产能，去派卡 |
| `超时` | `running` 超过面板阈值 | 核对进程、近期输出及产物；运行时间较长不等于卡死 |
| `唤醒异常` | 近期有 `deferred`/`failed` 唤醒 | 查 `reason` 再处置 |
| `N办/M审/K停` | 在办 / 待裁 / 停放（`backlog`+`blocked`） | 停放不算没动 |

### 面板本身可能说谎，先核它

面板第一版把 `backlog`（有意停放）算进「有活没动」，一次误报 4 个正常 Agent。**判定错误的面板比没有面板更危险**：它会让你去修不存在的问题，或者忽略真的卡死。

迁移到新环境时，先拿一个已知状态的 Agent 做对照，确认三类状态（在办/待裁/停放）都落对位置，再信它的汇总。

### 面板测不出来的，靠人补

| 盲区 | 补法 |
|---|---|
| 跑着但跑错方向 | 看 `running` 时长 **+ 工作区有没有新改动**（`git status`） |
| `in_review` 但没有交付物 | 打开卡核对产物，不信状态 |
| Agent 自报比事实乐观 | 每条 AC 配一条可复现命令 |
| 唤醒被静默挡住 | 查唤醒记录里的 `status` 与 `reason` |

## 2. 唤醒失败：四种已确认模式与处置

Agent「显示空闲但不动」几乎都不是能力问题。按顺序排：

| 现象 | 真因 | 处置 |
|---|---|---|
| 空闲但名下有 `todo` 卡 | 可能是状态残留、排队或唤醒未完成 | 先核对状态、运行和唤醒记录，再按获准的管理流程处理 |
| 评论唤不醒 | 唤醒可能被 `deferred`，例如 `reason=decision_pending` | 核实待答问题与已有工作；解除条件满足后再安排续接，避免重复派工 |
| 同一 Agent 两张卡并发 | 会话协调失败（`persisted active turn`） | **一个 Agent 同时只给一张卡** |
| Agent 反复重跑已完成的卡 | 在 `in_review` 卡上反复评论，每条评论触发一次 run | 不在已完成的卡上评论；必要时取消排队 run |

原则：先核实执行状态和阻塞原因，再选择获准的恢复方式；保留已有成果，避免重复执行。

## 3. 用对照组诊断，不要猜

判断「这个 Agent 坏了」之前，拿一个正常 Agent 对照：比运行记录、配置、唤醒状态。曾有 Agent 被误改配置，回滚后证明**原配置一直是好的**，真正原因在外部连接。

没有对照组的"修复"很容易把好的改坏。

## 4. 任务切分：让每个任务都有可见产物

一条卡应该让执行者在**每一步都留下可核对的东西**：

- **强制先红后绿**：先写会失败的测试并贴输出，再改代码。防止"改完就绿"的自证。
- **每步回报**：大任务要求每完成一步就在卡上回一句，而不是最后一次性交。
- **卡住就停**：明确写「如果你卡住，回一句『我卡在 X』就停」——**这比再跑 50 分钟有价值**。
- **范围单一**：一卡一缺陷。范围宽的卡容易在 50 分钟里零改动。

判断"跑得久"是否等于"卡住"的唯一可靠依据是**产物**，不是时长也不是状态。

## 5. 成本纪律：按能力分 lane，不是把活不干

| lane | 适合 | 不适合 |
|---|---|---|
| 便宜的免费模型 | **机械活**：跑命令原样回报、批量补路径、重复核对 | 判断、行号推定、跨文件推理 |
| 贵的强模型 | 关键路径代码、契约与并发语义 | 文档搬运 |

给便宜 lane 的任务必须**没有判断空间**：命令、期望格式、边界都写死；一次只给一个极小任务，且**同时只给一张卡**。

经验：便宜 lane 会把「路径补全」和「行号推定」混在一起做，**行号是它最容易编造的部分**。所以：

> 机械可验证的部分交给它；需要判断的部分自己留。行号一律用工具核，不靠猜。

## 6. 文档与引用的机器判据

```bash
scripts/dev-env/check-doc-refs.py            # 文档里的「文件:行号」是否存在/越界/歧义
scripts/dev-env/release-preflight.sh          # 上线前代码/契约/配置门禁
scripts/dev-env/final-acceptance.sh           # 端到端与人员判定（存在时）
```

`check-doc-refs.py` 的判定是**下限检查**：它只能证明"文件存在、行号在范围内"，**不能证明那一行就是文档所说的东西**。真正的判据仍是打开那一行读。

## 7. 验收：门禁必须会红

- 新写的门禁**第一次跑必须是红的**，否则它没在检查任何东西；
- 收紧判据时用**反向对照**：把被检查的东西退回修复前，门禁必须重新变红；
- 门禁说谎的两个方向都要防：说"绿"（漏报）和说"更差"（误报）——**后者会让人去修不存在的问题**；
- 文档说"已可用"、门禁说 FAIL 时，**以门禁与实测为准**，并改文档。

## 8. 并发与共享资源红线

- 同一文件、同一 worktree、同一引擎/端口**不得两人同时写**；撞车先核归属，不覆盖、不回退他人改动；
- 已知会被多人改到的"热点文件"（门禁脚本、总入口文档、契约）**指定唯一写者**，其余人提需求；
- 派工前先看目标卡和工作区是否已被占用，再决定落点。

## 9. 每轮结束时留下一件事

每轮必须留下**下次能被触发的依据**，否则这一轮的推进在下一轮就丢了：

- 依赖的具体事件（哪张卡完成、哪个 PR 合并、哪个人裁决）；
- 已配置的周期检查（若有）；
- 需要人工决策的事项，写清所需授权、影响和建议。

没有可用触发机制时，明确写出这个缺口，而不是假设"下次自然会想起来"。

## 10. 交接

用一页纸交接，包含：

- **当前目标**与判定它完成的标准；
- **关键路径**与主要交付缺口（按影响排序）；
- 每个 Agent 的**当前任务 + 下一项候选**；
- **阻塞清单**：解除条件、责任人、下一步动作；
- 本轮**已合并的 commit** 与仍未验证的结论（区分实测/文档/推断）。

不写流水账。"谁在什么时候改了什么"不如"现在是什么状态、下一步谁做什么"。

# Codex 会话与 subagent 交付 SOP

适用于选择执行方式、跨会话接续及多 Agent 交付；简单局部任务直接执行，不为使用本 SOP 新建计划、任务卡或审批。产品边界与授权遵循[根规约](../../AGENTS.md)，角色与环境边界见[多 Agent 协作](agent-collaboration.md)，检查范围见[验证指南](../agent-verification.md)。本页规定协作方法，不宣称宿主已部署这些规则或具备事件订阅能力。

## 一个目标、一位负责人、一条执行队列

- 承接当前工作的 Codex 会话按最新明确授权决定优先级、范围、AC 与产品接收；实际身份按用户当前指派核实，不从聊天标题、角色名或历史配置推断。其他会话、subagent 和外部执行通道只承担具名交付或独立审查。
- 每个可验收切片由一位交付负责人负责实现、提交或回传、PR、评审返修、验证、交接、解阻和工作区收尾；会话内局部任务默认由当前执行者负责，无需另设角色。这是技术责任，不增加产品排序权或二次审批层。承接会话可直接完成授权内的核查与修复，参与实现后仍须交适任非作者审查。
- PRD 保存完整产品要求，设计说明方案；GitHub issue 保存当前任务与 AC。subagent 返回值与外部执行通道的任务卡只承载本次执行，不成为第二份队列、AC 或门禁来源。会话内可完成的局部工作无需额外建卡；同一修复不同时派给多个执行位置。
- 当前范围通过 [PRD](../prd.md)、相关设计和[需求矩阵](../plans/delivery-tracking.md)关联到[总控 #336](https://github.com/hrygo/SpeechNexus/issues/336)下十个 MECE Epic；[关联源](../plans/delivery-issues.json)保留稳定需求、主责、实现/集成/验证及证据。实施 issue 可以为空；使用[按需规划技能](../../.agents/skills/speechnexus-next-delivery/SKILL.md)选择下一可验收切片，新卡原生直属唯一 Epic，随后登记并只读刷新状态。不在 GitHub 预建全部 backlog，历史仅在查证时读取。
- Goal 写明对应目标、获授权阶段的交付物、接收条件和停止条件。等待时保存恢复点；外部条件未满足不得宣称完成，也不靠自动续行反复查询或寻找无关旁支。

## 按反馈和环境选择执行位置

| 路由 | 适用工作 | 交付与约束 |
| --- | --- | --- |
| 当前 Codex 会话直接执行 | 局部修改、明确修复、需要用户即时查看或频繁纠偏 | 在同一候选完成必要检查；不因耗时长就另加管理层 |
| 当前执行者按需使用 subagent | 可独立的定位、日志分析、反证或文件范围清楚的实施 | 传明确问题、必要版本、读写范围与预期结果；返回结论、依据、未验项，不复制整段聊天和原始日志 |
| 宿主提供的多路编排 | 多个互不依赖的只读调查、批量审阅或文件范围互斥的实施 | 每路给独立输入和唯一写者；合并结果时核对版本，不把并行数量当产能 |
| 委托 Linux GPU Agent（Paperclip，可选） | 需要真实 GPU、Linux aarch64、隔离数据库 / 对象存储，而本机不具备 | 派发前确认输入可取得、通道可达、具名执行者和接收者；任务卡只承载本次执行，结果核对后落回 issue / PR；密集返修留在原切片 |

任务长短只是信号；按反馈密度、环境需求、可独立性和交接成本选路由，不要求每种机制每次全部参与。新建用户可见的 Codex 会话按用户请求执行，不把它当自动派生的后台工作单元。

外部执行通道不是必需依赖：本机或 subagent 能完成的工作不因通道存在而外派，仅在环境确有需要时使用。平台任务状态、编号和面板不构成项目队列、AC 或门禁，交付以 issue / PR 中的实际候选和证据为准。

subagent 的上下文、工作区、工具与权限以宿主实际能力为准，不假设它自动获得独立 checkout 或隔离环境，也不假设它可见当前对话；需要共享历史时按宿主能力选择继承上下文的派生，并在记录中注明。同一文件只有一名写者；需要并行检出时使用各自 worktree，数据库、端口和共享资源另行安排。各执行位置合并计算并发和主机窗口，沿用最多两个无写冲突开发切片及同一写者一次一个切片的限制；增加调用层数或外部通道不增加额度。

## 最小上下文与执行步骤

需要交接时沿用任务正文和已有制品清单，仅补本次路由与风险适用的信息，不新增一套表单。直接回答不要求候选或 reviewer，纯文档不要求运行环境，不涉及注册角色的工作不要求能力卡；不适用项不构成门禁。真正缺少的必要输入只阻塞依赖它的动作。

| 信息 | 最低需要 |
| --- | --- |
| 目标 | issue / AC 或用户请求、当前场景、预期结果、本次范围 |
| 候选 | 实际 base、目标分支、候选 SHA 或完整补丁及正式入口 |
| 责任 | 交付负责人、唯一写者与文件范围、适任非作者 reviewer、接收者；回传路径另指定集成写者 |
| 条件 | 实际执行位置与身份、执行环境、已有授权与资源窗口、必要检查、接收路径和停止条件 |
| 恢复点 | 已完成、失败 / 跳过 / 未运行、证据位置、具体阻塞及下一动作 |

1. **确认目标与输入。** 只读本次相关规则、issue、版本和证据；同一会话复用仍有效材料，新会话按恢复点补读变化。历史原因用项目记忆，当前实现用代码与实测；不把历史结论作为当前状态。
2. **确认可执行。** 按实际动作核对版本、工作区、授权与所需资源；使用 subagent 时核对模型、工具与文件权限，使用专用环境或外部执行通道时核对目标环境可用性与当前任务能否启动。在最终执行位置验证依赖与缓存访问、必要命令启动及产物往返；已有同模型、工具链、依赖与相关策略的有效回执可复用；首次使用、配置 / 环境变化或失败后再做最小预检，不为每次派工固定新建探针卡。涉及共享资源时仍须核当前余量。
3. **完成一个候选。** 作者在原切片实施、自测并修复问题；有意义且通过适用基础检查的增量按授权提交、推送并创建草稿 PR，不必等全部 AC 或目标环境资格。具备能力时作者贯穿原 PR 返修；只能回传时由预定集成写者核验接入并贯穿原 PR。补验和返修更新同一清单。只有独立交付、责任人 / 环境边界确实需要时才拆执行位置，记录输入和接收关系；单纯等待和重复检查不拆卡。
4. **按风险审查与验证。** 草稿出现后按预定接续安排并行独审与适用验证；审查安排由承接会话在派工时预定，作者不自行选择 reviewer 或另建审查队列。固定受检候选，非作者检查适用边界；高风险仍须合格非作者与对应环境验证。审查 PR 只承载审查产物：审查分支基于 `origin/main` 拉出；提交前 `git status --porcelain` 只应列出 `docs/reviews/` 下的报告文件，提交后用 `git diff origin/main...HEAD --stat` 确认只含 `docs/reviews/` 下的报告文件——前者覆盖未跟踪与已暂存文件（`git diff` 一律看不见未跟踪文件），后者取三点口径按 merge-base 比较，不把主干前进算进本分支。被审内容用 `git show <被审 head>:<path>` 读入管道或写到仓库外路径，不写回仓库内路径，也不在审查分支上检出被审改动。审查分支从被审 head 拉出会把实现带进审查 PR，squash 合并后实现以审查标题进入主干；本仓库已发生审查 PR 携带的恰是被审字节、而该实现最终以另一份修订版合并的情形，被审代码与进主干的代码因此不是同一份（实证：[2026-11-13-commit-classification.md](../reviews/2026-11-13-commit-classification.md)，squash `f88279dc`）。代码评审与独立运行验收分别判断，subagent、换角色名或继承同一上下文都不自动满足作者、模型或环境独立性。独立运行验收按任务适用条件使用不同主机、不同数据库大版本或不同取码路径；同一环境原样重跑只记复测。
5. **接收并收尾。** 接收者实际取得候选与证据，核对版本和适用检查。已授权 PR 交付的代码阶段以精确 head 的非草稿待合并 PR、适用检查与独审无阻断及接收为终点；其他任务按约定交付，不因本 SOP 扩大 Git 授权。调查 / QA 按约定接收报告和原件，无需制造 PR。分别记录技术阶段、完整产品 AC 与合并授权 / Gate；获准后沿原切片合并并核验主干，GitHub issue 仅在主干包含成果且完整范围与 AC 满足时关闭。按下节清理临时工作区并交回执，合并后再次核查剩余分支与保留项，不额外建立长期队列或重复唤醒已结束工作。

派发 subagent 时一次给全目标、受检版本、可写文件、期望产物（结论 / 补丁 / 报告）、需回写的 issue 字段和停止条件；不把整段聊天或未整理日志当输入。返回值按实际产物复核，不直接采信自述；结论与证据落在 issue / PR 或文件中，不留在会话里。

委托 Linux GPU Agent 时，任务卡承载本次执行，队列与 AC 仍在 GitHub issue。派发前核对通道可达、GPU 环境与台账条件、输入可取得及具名接收者；回执只算执行结果，须由接收者核对候选、命令、退出码和限制后落回 issue。平台状态失败而产物已就绪时先核原件，只处理状态，不重跑业务；同因权限 / 唤醒失败保留诊断交通道维护者，不反复派发同一任务。

## 工作区生命周期与收尾

工作区服务于当前交付，成果与恢复证据放在可独立取得的位置；任务结束后不靠保留整棵目录保存交付物。此处「工作区」同时涵盖 Codex 会话、subagent 与外部执行通道的临时 worktree、独立 checkout 及隔离恢复目录，清理范围和权限仍按根规约及当前授权判断。

- **创建前核对。** 默认保留主工作区，每个实际在办、具名且无写冲突的开发切片最多一个临时工作区；沿用最多两个开发切片的总额度。只读 subagent 优先读已有候选；独立验收确需新 checkout 时，在原任务注明环境、负责人和使用窗口。重试或替换执行前先处置旧 run 与工作区，不绕过隔离另建副本。
- **原任务负责。** 创建时沿用原 issue 登记路径或分支、base 和交付负责人，不另建台账。执行者完成原进程与回传的收尾，接收者确认成果可取得，交付负责人负责最终清理；跨机器或缺少远端权限时指定具名操作者，不能把「已回传」当成已清理。
- **同轮处理。** 完成、失败、取消或被替代时即核查，不等下一批派工或阶段结束。PR 候选和独有文件已可靠保留、无运行或验收引用时，可在 PR 合并前移除本地临时目录；保留仍需使用的 PR 远端分支与证据。合并后按实际 head 与合并结果复核剩余本地分支，远端分支删除另核授权。

按以下顺序完成一次收尾，复用仍有效证据；纯读取且未创建临时资源的任务记「不适用」，不额外打包或建恢复卡。

| 步骤 | 必须核实与处理 |
| --- | --- |
| 1. 固定对象与停止证据 | 对齐项目、issue / 任务、工作区路径、branch / HEAD 和现有使用者。核查 subagent、子进程、服务、回传及 Git 操作；任务终态、PID 消失或旧租约到期各自不能单独证明全部已停止。主工作区、用户保留项、其他任务及仍在用目录保持。 |
| 2. 保全独有成果 | 核验主线包含关系，或远端 PR 实际 head / 已接收候选；squash、旧分支或分叉进一步比较实际差异。保存 staged / unstaged 修改、新文件和必要 ignored 内容；需要恢复时保留 refs / bundle、索引及有价值的 mode / symlink / 扩展属性，校验摘要并按风险验证恢复。Git bundle 不替代文件备份，补丁不替代未跟踪文件。 |
| 3. 结清文件恢复 | 按原执行身份核实回传、接收、文件收尾及未决操作。已停止且文件可独立恢复时，允许如实完成文件收尾，同时保留业务失败、未知费用和有效恢复记录；不为清理伪造业务成功、complete 用量回执或零费用。 |
| 4. 清理与平台同步 | 优先使用所属应用的生命周期入口，按授权解除过期绑定、归档并移除临时目录；普通 worktree 使用 Git 支持的移除流程，独立目录优先可恢复地移入废纸篓。只删除有保留证据且无使用者的本地分支；不批量强删、不因远端分支消失就直接 prune。外部执行通道的任务记录按其可用接口收尾，不作为项目完成条件。 |
| 5. 回读与交回执 | 确认原目录已移除、`git worktree list --porcelain` 无该注册、目标分支按预期处理、issue / PR 记录已更新且无遗留引用。保留仍有效的历史关联与业务 / 计量事实。记录已收尾但目录还在、目录已删但 issue 仍开放，均属于未完成的收尾。 |

清洁且提交已可靠保留的目录无需额外全量备份。只可排除已确认可重建的依赖与缓存；不能仅因文件被 ignored 就丢弃未知内容。证据、敏感文件和必要运行数据保存在获准的仓库外位置，不把备份混入产品提交。

回传、文件收尾或清理卡住时，由具名维护者按精确对象修复原操作；没有关闭接口不是处置终点，应定位支持入口或提出可审查、可回退的定向维护。维护须保留停止证明、before-image 与审计，并遵守原锁 / fencing；本 SOP 不授权绕过权限、直接改数据库、清空会话、改预算或恢复调度。已停止的临时检出，在成果保全、文件回传 / 收尾与所需租约释放按原协议核验后，未知账务保留为账本中的独立待处理项，不单独构成无限保留目录的理由；仍依赖原目录的未决操作继续按具名例外跟进。

确需保留时，在原任务或既有交付回执写明路径、具名负责人、保留原因、成果保留处、解除条件及下一复核时间，默认在 24 小时内复核。时限是处理与升级要求，不是删除 TTL；到期仍未解除时，交付负责人推进具体修复或交承接会话明确保留决定与新期限，不自动续期。接管及下一次派工前复核已有保留项；同一切片的旧工作区处置未明确前，不再启动其替代执行或创建新副本，无关独立工作可继续。

最终报告沿用一行：`工作区收尾：已清理 / 不适用 / 保留（对象、负责人、原因、成果位置、解除条件、下次复核时间）`。业务 issue 仍按完整范围与 AC 判断；业务已交付但资源尚未收尾时分别说明，不能宣称「全部完成」。用现有任务时间戳、交付 / 合并事件和下一次接管检查触发收尾，不因此安装新 timer、巡检任务或新增审批层。

## 同版证据与最小充分验证

- 每份结果绑定精确候选、相关契约 / 迁移 / 依赖、环境、命令与原始结果。复用取决于相关源码 / 制品字节、输入、工具环境与检查配置及覆盖结论；仅 commit 元数据改变无需重跑同字节检查。候选变化记录新增差异及受影响结论，仅补验失效部分；无法证明仍适用的历史结果保持历史，不转算当前通过。
- 测试按既有命令和实际副作用分组确认边界，记录允许的子进程、文件、网络、隔离与清理。内存 ASGI transport 本身不等于启动监听服务；临时 loopback、子进程或数据库仍须在实际授权内。不能因措辞含混把整组安全测试永久挂起，也不能凭「测试」二字扩权。
- 分批执行维护同一份测试清单与累计覆盖；通过、失败、跳过和未运行分列，未运行项给具体原因及解除条件。已执行组无需每轮重报逐节点清单；定位遗漏或歧义时再展开，不把分批结果宣称为同版全套一次实跑。
- 制品在获准存储发布后供接收方按权限取得并核验；已有同版原件与有效核验可复用，不为每次转述重新打包、上传或全量复测。正式入口不可访问时交提供方 / 维护者修复，不借他人私有工作区或绕过权限取件。
- 保留真实引擎、正式消费者、隔离持久行为和物理拓扑等原验收范围；issue 附件、绿色 CI、局部 done 各自只证明覆盖范围。

## 等待、汇报与故障恢复

优先使用宿主实际可用的完成、失败或需用户处理事件：subagent 完成会主动通知，后台作业按作业结果等待，外部执行通道按可用的回执或状态事件等待；没有可靠事件入口时才在现有授权内做有界状态查询，记录下一检查条件。不新建 timer、轮询任务或反复读取完整日志；没有新事实时保持安静，持续工作仍遵循宿主必要进度沟通要求。

长任务在任务内约定与规模相称的进展检查点，报告已产生的候选 / 证据、剩余工作和阻塞，不只报告「仍在运行」。对用户在交付、关键验证结果、实质阻塞、风险变化或需要决定时汇报；保留失败与限制，不以消息频率代表进展。

配置、鉴权、工作区和宿主错误由具名维护者处理；相同权限或状态原因首次出现即保留诊断并交受理者，只有原因实际修正后重试。产物已完成但状态失败时先由接收者核验原件，只处理状态，不重跑业务。阻塞记录包含已确认事实、影响、责任人、下一动作与新证据要求；输入或原因改变后再续行，继续可独立完成的工作。

旧进程停止、checkpoint 或未决操作结果不明时保留隔离和原产物，不靠清空会话、换 Agent 或新任务重放。获准操作者先取得停止与操作结算证据，再决定原任务续行或带恢复点移交。宿主只允许查看或要求用户处理时，任务授权不绕过该边界；本 SOP 不授权修改宿主配置、鉴权、权限或运行配置。

阶段收尾利用已有时间戳、任务记录比较：从就绪到可接收交付的时间、阻塞时长、重复交接 / 验证、返工和模型费用；缺记录标未知。以可接收交付和遗留风险评估效果，不以任务数、报告数、活跃 Agent 数或测试总数证明效率提升，不新增常驻统计任务。

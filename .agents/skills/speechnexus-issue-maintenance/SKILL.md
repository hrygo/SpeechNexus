# Issue 起草与维护

交付保留报告者问题与有效证据的当前正文，或范围、任务与 AC 明确的实施任务。贡献入口见[贡献指南](../../../CONTRIBUTING.md)，先读[正文规范](references/issue-body.md)选择适用格式；不因整理文字而探索代码、执行业务测试或扩大实施范围。

缺陷报告和建议收集问题、复现或期望结果，保留表单结构与原始事实。实施任务默认边界清晰、可由一个 PR 完整解决，四部分简洁表达即可；确有独立交付或联合验收需要时再拆分。模板、四部分与标签映射是项目约定，不作为关闭有效反馈的理由。

## 按请求执行

- **起草/建议/审查：** 输出可评审正文或问题清单，保持远端只读。
- **已授权创建或编辑：** 核对仓库、目标 issue 与本次允许改的字段，再执行。只改正文时保留标题、state、标签、负责人、里程碑、Projects 字段和原生关系。
- **已授权分类或关闭：** 读取合并技能的[状态与证据](../sync-issues-after-merge/references/status-and-evidence.md)，按真实解决、重复或不计划等原因处理；普通反馈不强制补 `status:*`。创建标签、原生关系或自动化须有相应授权。
- **合并收尾或补同步：** 使用 [sync-issues-after-merge](../sync-issues-after-merge/SKILL.md) 核实主干集成、任务/AC 与状态，不重复执行两套写入流程。

优先用可用的 GitHub 连接器；能力不足时使用已认证的原生 `gh`。不读取令牌或新建鉴权配置。无访问权限时交付草稿及未完成项。

## 更新与核验

1. 读取最新正文、必要关联和已链接证据，先识别反馈或实施任务。创建前检索相同问题；重复时保留原始报告和主 issue 链接，不擅自新建、关闭或改关系。独立小 issue 只维护本项；实际属于 Epic、工作包或 Gate 时才展开层级规则。
2. 按适用格式就地改写、去重并检查信息量与长度。缺复现或证据写明具体待补项；实施任务区分交付与 AC，不为关闭降低要求。保留报告者的复现、预期/实际结果与关键讨论；范围变化必须有请求依据。
3. 写前即时重读正文与更新时间；出现并行修改时保留新内容。同段意图不明则暂停该项，继续独立项；可合并时刷新后重算一次，仍冲突则报告。
4. 使用结构化字段更新；`gh` 的多行正文先写 UTF-8 临时文件，通过 `--body-file` 传入，不把正文拼进 shell。结果未知先查询当前值，不盲目重放。
5. 写后回读适用结构、原始事实、勾选依据、原有要求、依赖和允许变更的字段。没有事实变化时不重复写入；已授权发布的重要决定或关闭理由应有可追溯记录，避免重复通知。

最终给出目标链接、实际修改与回读结果、剩余事实或验收缺口。只起草时明确未写入；失败或持续冲突时报告具体未完成项。

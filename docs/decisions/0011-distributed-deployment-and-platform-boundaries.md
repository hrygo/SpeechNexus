# ADR 0011 分布式部署单元与平台边界

## 背景

SpeechNexus 已按集群原生架构划分 API、工作台、调度、执行网关、节点控制器与推理引擎，
但部分产品说明仍把整个系统概括为 Linux 应用，当前 Compose 也只提供单节点 bootstrap。
同一 workspace 内的 Linux 媒体沙箱类型错误，容易被误读为所有业务入口都依赖 Linux。

用户已确认整体采用分布式部署，各模块无需集中在一台主机；平台要求应由部署单元的
实际职责决定，推理与节点执行环境的依赖不应扩散到业务和控制服务。
后续审查以用户明确的“松耦合、尽量跨平台”为目标，进一步区分必要的一致性边界与可移除的装配耦合。

## 决定

1. **以部署单元界定平台要求。** Speech API、Workbench API、实时接入与通用调度/任务
   逻辑保持独立服务边界，不依赖本机 GPU、推理进程或 Linux 专属内核 API。
   macOS、Linux 的原生应用运行能力分别验证；共享源码或镜像不代表必须同机部署。
   角色可以共用经裁剪的制品或明确托管后台循环；不为每个逻辑角色强制增加远程服务。
2. **保留当前 Linux 算力路线。** 当前选定的 CUDA / vLLM、vLLM-Omni、节点容器控制及
   引擎扩展按固定 Linux 组合验证。Gateway 绑定受管节点与引擎入口；Controller 绑定实际
   容器 daemon，业务 API 与工作台不接管这些权限。不在本决定中新增推理平台适配。
   Gateway/Controller 的协议不要求调用方使用 Linux；当前节点实现的本地锁、daemon 与
   引擎归属是实际放置约束，不能仅将端点改成远程地址就宣称可迁移或无状态扩容。
3. **隔离媒体处理的平台依赖。** 现有音频检查沙箱依赖 Linux，但不需要 GPU。
   应把它作为明确的 CPU 执行组件封装，保持业务服务的平台独立性。具体服务化形态和跨机
   协议仍待设计；现有本地文件描述符接口不自动成为远程接口，不降低隔离或停止证据要求。
   优先比较复用受控 Linux 检查 worker 与独立服务，选择满足权限、预算和恢复要求的最小形态。
4. **维持原有状态和内容边界。** PG 是全局产品权威；完整配方准入与 Job/outbox 保持
   同一事务域。对象存储承载跨单元持久内容，实时流走既有网络协议；节点本地锁和控制器
   回执不变成第二协调权威。独立服务不等于任意跨库拆分或共享宿主目录。
5. **区分设计、制品与验收。** 单节点 Compose 仍是开发验证拓扑，多机是明确交付目标。
   原生跨平台、容器部署、模块导入、真实模型和多机故障资格分别取证，不互相替代。
   部署单元清单、当前入口和未交付项维护于[部署单元规划](../architecture/deployment-units.md)。

## 与既有决定的关系

- 延续 [ADR 0004](0004-cluster-ready-architecture-and-single-node-mvp.md) 的独立角色、
  节点身份、固定会话 owner、网关屏障与受限控制器。其单机 MVP 描述保留为验证拓扑，
  不作为要求所有产品组件同机或使用同一操作系统的限制。
- 延续 [ADR 0006](0006-cluster-coordination-and-storage-portability.md) 的集群要求、
  单一事务权威、PG 正式适配器与 MySQL 关键协调测试边界，不引入新的协调服务。
- 保持既有公开/内部机器契约、内容网络边界与首期共享访问范围；不增加新路由、状态、
  身份系统或部署自动化授权。

## 影响与验收

产品主设计、README、技术方案与部署入口按部署单元描述平台要求。
后续实施补齐独立服务入口、代理上游、配置与依赖制品；媒体服务化先完成边界和契约设计。
保留当前开发脚本的 Linux ARM64 限制，同时明确它只说明该开发环境。

`accepted` 表示部署与平台设计基线已确认。业务/控制面原生平台兼容、完整跨主机链路、
真实引擎故障恢复与生产高可用尚须独立实现和验证；本决定不宣称现有 Compose 已完成它们。

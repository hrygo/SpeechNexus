# 双中心生产架构：定案与改造方案

前提已定：主备数据库、异步复制（接受丢失）、两中心都有 GPU（第四范式智算平台提供）、
中心级灾难人工切换、无状态服务双活。开发环境用 macOS k8s 模拟其中一部分。

## 一、定案与直接后果

| 决定 | 直接后果 |
| --- | --- |
| 数据库单主 + 备，不做双写 | 只有一个写入点；"唯一权威库"得以保持，不需要重审数据模型 |
| 数据库与对象存储（S3）生产由其他团队提供，按 SaaS 消费 | 复制、切换、备份、容量都变成供应方职责；我们保留的是端点切换与数据可导出 |
| 异步复制，接受 RPO>0 | 切换会丢最近若干秒的租约与预算；**必须用对账收敛，不能信任库里的状态** |
| 两中心都有 GPU，由智算平台提供 | 控制器不再是容器运行时，而是平台 API 的客户端；开发环境无法验证这条路径 |
| 中心级灾难人工切换，无状态服务双活 | 两个中心都在跑计算，但只有 A 的库可写；切换是一次有脚本的人工操作 |
| 双活且同中心优先 | 调度先看本中心余量，不足才跨中心；跨中心执行要把制品取过来，因此放置必须同时看数据位置 |

## 二、目标形态

两个中心跑同一套组件，都连 A 中心的主库；B 中心的 PostgreSQL 备库只用于灾难切换。
同城 RTT 低，跨中心访问主库是可行的，但**每一次提交都跨中心**，这个代价要进超时预算。

```
中心 A（生产）                        中心 B（同城）
  api / workbench-api / worker  ──┐     api / workbench-api / worker
  gateway / dispatch              │       gateway / dispatch
  PostgreSQL 主  ◀────────────────┘       PostgreSQL 备（异步，仅 DR）
  对象存储（本地）                        对象存储（本地 + 单向同步）
  GPU（智算平台）                         GPU（智算平台）
```

切换是把"写入口"从 A 的主库换成 B 提升后的主库，并让两侧组件重新连接。所以
**连接端点必须只有一处定义**，且可在一个动作内切换。

## 三、接受丢失之后的语义处理（本文最重要的一节）

异步复制意味着切换时最近 Δ 秒的事务可能不存在。丢掉的不只是数字：

- 一条租约记录不存在了，但对应的引擎可能仍在运行，仍在占显存。
- 一次释放记录不存在了，但预算在切换前已经退回。
- 一条 Job 的完成记录不存在了，但制品已经写进对象存储。

因此**切换后不能信任任何在飞状态**，必须做一次对账：以引擎与对象存储的实际观测为准，
重建归属，再恢复准入。

具体要求：

1. 控制器启动时强制跑一次全量观测，不接受"库里说它已停止"作为停止证据。
2. 一个提交的幂等键在切换后仍然有效：重放返回原执行，不新建（现有 intent 机制已具备）。
3. 预算与配额以观测结果收敛，不以库记录为准。
4. Δ 必须有上限并被写出来：超过上限的丢失量意味着切换不可接受，转人工处置。

## 三之二、外部依赖的责任边界

数据库与对象存储生产不由我们部署。这改变的是责任划分，不是架构——组件仍然在同一套协议和
同一份 schema 下工作，但**谁能修什么时候修**变了。

| 事项 | 生产归属 | 我们保留的 |
| --- | --- | --- |
| 主备复制与 promote | 供应方 | 确认其复制模式与 RPO 能否满足 Δ 上限 |
| 中心级切换 | 供应方执行，我们配合 | 重新指向端点的动作与验证 |
| 备份与时间点恢复 | 供应方 | 自持逻辑导出（防误删、防合约终止）；已实测可恢复 |
| 连接池与连接数 | 双方约定上限 | 两中心合计的连接预算 |
| schema 与迁移 | 我们 | 迁移的执行时机与两阶段拆分 |
| 数据导出 | 我们 | 能随时全量导出并在他处恢复 |

三条硬要求：

1. **必须能提供单一可切换的写端点**。若供应方只给两个独立连接串，切换就得改所有组件的
   配置，我们的"写端点单一定义"这一层反而是唯一能兜住的地方。
2. **必须确认跨中心复制存在**。数据库服务商通常只保证单实例高可用（同机房主备），
   这与"同城双中心"不是一回事。若只有单中心，灾备中心的应用连不到库，双活就不成立。
3. **数据可导出必须现在就验证**，不要等到需要迁移时才发现某个扩展或大对象导不出来。

对象存储是一个 S3 协议端点：生产由其他团队提供，实现与高可用不在我们职责内；开发环境用
MinIO 模拟。对我们而言它退化成一项配置（endpoint、bucket、凭据），不是架构组件。

我们只对四件事负责：

1. **endpoint 必须在内网**，否则内容出网，违反既定的内容边界。
2. **只经 S3 API 读写，不挂本地目录**：进程之间不通过共享文件系统传递业务内容。
3. **制品引用是对象键而不是路径**，这样换端点、换中心都不改数据。
4. **预签名有效期与分段上传的中止**由我们决定，不假设对方兜底。

写入后立即可读是 S3 协议自身的语义（2020 年起 S3 即为强读后写一致），跨中心的可见延迟与
复制方式属于对方的高可用范畴，不进入我们的验收。

开发环境在本地部署这两种依赖，因此**无法验证供应方的任何行为**。这部分只能靠对供应方沙箱
做契约测试，不能靠本机模拟——这是模拟器最实在的一条边界。

## 三之三、导出与恢复演练（已实测）

在开发环境对当前数据库做了一次真实演练：`pg_dump -Fc`（去掉属主与 ACL），恢复到另一个
全新的 PostgreSQL 实例，逐表比对行数。

| 检查 | 结果 |
| --- | --- |
| 表数量 | 119，两侧一致 |
| 逐表行数 | 119 张全部一致 |
| 大对象 | 0，不涉及 |
| 编码与排序 | UTF8 / `en_US.utf8` |
| 扩展 | 仅 `plpgsql`，无外部依赖 |

演练暴露的**唯一真实缺口**：带 ACL 的恢复需要角色先存在。往一个没有这些角色的集群直接恢复会失败，
报 `role "speechnexus" does not exist`（`ALTER SCHEMA ... OWNER TO speechnexus`）。

因此恢复顺序是固定的：**先跑角色 provisioning，再恢复**。角色不在 dump 里，这是设计使然
（`deploy/cluster/provision-roles.py` 是角色的唯一定义点），但迁移文档必须写明，否则接手的人
会在第一步卡住。

结论：数据可导出且可重建，迁移路径通畅；依赖顺序是角色 → 结构 → 数据 → 授权。

## 四、PostgreSQL 版本

现状是 16 线（`deploy/compose.yaml:59` 与 `deploy/cluster/versions.env:17` 均为
`postgres:16.15-alpine`）。

截至 2026-11-21 核验：PostgreSQL 19 已于 2026-11-19 正式发布
（[发布公告](https://www.postgresql.org/about/news/postgresql-19-released-3449/)），距今两天；
18 线已有多个小版本。

**已定：生产用 18 的最新小版本，不追 19。**理由不是保守，而是两天的新大版本没有任何小版本
修正，而双中心切换依赖复制与 promote 的稳定性，这是最不该做首日验证的部分。

19 不作候选：一个没有小版本修正的新大版本，不适合承载切换演练。

从 16 到 18 的迁移是主版本升级，不是改 tag。需要 `pg_upgrade` 或逻辑导出导入，并覆盖：
迁移链在目标版本重放一次、`SKIP LOCKED` 与事务语义不变、PostgreSQL 侧的角色与授权脚本重跑。

## 五、"无状态服务双活"的真实边界

双活的是进程，不是延迟。

- `api` 是写服务。B 中心的 api 每次准入提交都跨中心到 A 的主库，同城 RTT 直接进入准入耗时。
- worker 双活是安全的：抢占式取任务（`backend/src` 里 120 处 `SKIP LOCKED` / `FOR UPDATE`）
  让两个中心天然互斥。但切换后所有 worker 必须重连，不能持有旧连接继续提交。
- 连接池要看住：跨中心连接变多，池上限与主库 `max_connections` 要按两中心合计算，
  而不是各配一份 50%。

**同中心优先**是放置规则，不是路由规则：准入时先看本中心的引擎余量，够了就本地执行；
不够才允许跨中心。跨中心执行有一个前提——制品要在执行中心可见，否则等于把音频搬运塞进
作业路径。因此放置的输入是三者：本中心余量、对端余量、制品位置。

准入记录必须带上执行中心，否则切换后无法判断哪些执行属于哪个中心。

## 六、引擎与智算平台的接口

### 平台是什么（2026-11-21 核验）

范式（原第四范式）的 GPU 管理底座是 **HAMi**——由其主导并开源的异构算力管理项目，实现为
Kubernetes 的 device plugin 与调度器扩展；新一代是 **HAMi-DRA**，接 Kubernetes 1.34 起 GA 的
动态资源分配（DRA）模型。对外产品（PhanthyCloud / 先知 AIOS）在这一层之上提供 GPU 细粒度
虚拟化、独占/共享/超分三类资源池、算力切分到 1%、显存切分到 M 级别。

也就是说：**平台就是一个 Kubernetes 集群**，外加更细的 GPU 切分与调度。它不是一套私有 API。

来源：[IDC 2026 评估与平台能力](https://www.ncsti.gov.cn/kjdt/scyq/zgckxc/zgcdt/202610/t20261014_258267.html)、
[HAMi 与 DRA 的结合](https://m.cnstock.com/commonDetail/573413)、
[先知 AIOS 5.1 的切分粒度](http://www.4paradigm.com/content/details_10_46967.html)、
[HAMi-DRA 实践](https://aicon.infoq.cn/2026/shenzhen/speaker/10505)。

### 由此修正的三个判断

**1. 不需要 `PlatformRuntime`。**

原方案设想"平台 API 客户端"，那是把平台当成外部服务。既然是 k8s，生产实现就是
`KubernetesRuntime`，两个实现足够：

| 实现 | 用途 |
| --- | --- |
| `DockerRuntime` | 开发环境（无 GPU 共享平台时） |
| `KubernetesRuntime` | 生产，也是平台的唯一接入口 |

少一个适配器，也少一层语义翻译。

**2. `--gpu-memory-utilization 0.25` 不是"放错位置"，是机制不对。**

先把机制说清楚：这个参数是"按**容器能看到的显存总量**的百分比预分配"。而平台限制显存有三种
做法，容器的可见量各不相同：

| 平台做法 | 容器看到的显存 | `0.25` 的实际效果 |
| --- | --- | --- |
| 给容器划独立分区（device plugin / HAMi vGPU） | 只有自己那一份，如 6 GiB | 6 × 0.25 = 1.5 GiB，远小于需要 |
| 预分配凭证（DRA ResourceClaim） | 同上 | 同上 |
| 只贴软限制标签（`CUDA_DEVICE_MEMORY_LIMIT`） | 整卡 48 GiB | 48 × 0.25 = 12 GiB，撞到别人 |

同一个数字在三种做法下效果相反，所以这不是调参问题。

vLLM 的这个参数按**可见显存总量**的比例预分配。平台若用 device plugin 把显存切成固定档位、
或用 DRA 声明显存额度，容器看到的显存本就是受限的，此时再用比例参数是把两层限制叠加，
结果不可预测。

**不必等平台方回答**：跑一次探针 Job 就能测出来——打印 `nvidia-smi` 的显存总量、容器内的
限制环境变量、以及节点上可用的 GPU 资源名。三种做法在这三项上的表现互不相同，一次就能定。
探针可以在平台的任意命名空间里跑，几十秒出结果。

确定之后按对应写法落清单：

| 切分机制 | 资源声明 | vLLM 参数 |
| --- | --- | --- |
| device plugin 资源名（HAMi vGPU） | `nvidia.com/gpumem`、`nvidia.com/gpucores` | 让 vLLM 用受限视图，比例参数取接近 1 的值 |
| DRA ResourceClaim | `resourceClaims` | 同上 |
| 软限制（`CUDA_DEVICE_MEMORY_LIMIT`） | 普通 `limits` | 可用比例参数，但需按受限总量折算 |

三种写法互不兼容，这是必须问清的第一件事。

**3. 两套独立平台 → 放置是"选集群"，不是"选池"。**

两套平台互不相通，因此跨中心调度没有平台层支持，必须由我们决定并把结果记进准入记录。
"同中心优先"的落地形式是：本中心优先，跨中心回退需要显式配置且只在制品已在对端时成立。

**4. 池的选择是产品决策，不是实现细节。**

平台提供独占/共享/超分三类池，且允许超分。ASR 批处理适合共享或超分池；实时链路对延迟敏感，
通常要独占。超分意味着尾延迟不再是常数：显存超分在空闲时无感，并发上升时表现为排队。
模板里的 `allowed_pool_ids: ["asr-batch"]` 已经抽象了池的概念，需要映射到平台真实池名。

超分比会直接影响尾延迟：显存超分在空闲时无感，在并发上升时表现为排队。这条要在容量模型里
显式写出来，而不是当成平台的默认行为。

### 定案：按"容器独立分区"设计

假设平台把显存切成独立分区，容器只看得见自己那一份。在这个前提下：

**1. vLLM 的比例应接近 1，不是 0.25。**

容器看到 6 GiB，`--gpu-memory-utilization 0.9` 表示"用这 6 GiB 的 90%"。分区语义下这才是
正确用法——平台已经限制了上限，vLLM 只需在额度内尽量用满。写 0.25 等于只申请到 1.5 GiB。

**2. 显存额度是资源请求，不是启动参数。**

额度要作为容器资源声明提交（平台的 GPU 显存资源名），vLLM 不负责限制。两者分工：
平台限制可见量，vLLM 在可见量内分配。

**3. 留出配置开关，因为开发环境没有分区。**

开发机的 GPU 是整卡共享，没有切分。同一份模板要能同时服务两种环境，因此引入三个环境键
（都在 `.runtime/cluster/compute.env`，不进仓库）：

| 键 | 含义 | 生产（分区） | 开发（整卡共享） |
| --- | --- | --- | --- |
| `ENGINE_GPU_MODE` | 显存由谁限制 | `partitioned` | `shared` |
| `ENGINE_GPU_MEMORY_MIB` | 容器可用的显存额度 | 平台配给值，如 `6144` | 整卡的一部分，如 `6144` |
| `ENGINE_GPU_UTILIZATION` | vLLM 可用的可见量比例 | `0.9` | `0.125` |

`partitioned` 与 `shared` 的差别只在第三个值：前者是"额度内用满"，后者是"整卡里只占这么多"。
模板本身不出现任何数值，只声明从哪个键取值。

**4. 校验规则。**

`check-parity.py` 增加一条：提交树里的引擎模板若出现 `--gpu-memory-utilization <数值>`、
`gpumem` 资源名的数值、或写死的显存字节数，判红。理由与集群地址相同——数值来自部署环境。

### 实现落点

| 文件 | 改动 |
| --- | --- |
| `node-controller/src/speechnexus_node_controller/domain/templates.py` | 模板新增可选字段：取自哪个环境键 |
| `.../infrastructure/template_config.py` | 解析该字段（`extra="forbid"` 需同步放宽） |
| `.../infrastructure/docker_runtime.py` | 拼命令时按模板声明注入 `--gpu-memory-utilization`；命令已显式携带则不覆盖 |
| `deploy/cluster/compute/approved-templates.json` | 删除 `--gpu-memory-utilization 0.25`，改声明环境键 |
| `deploy/cluster/init-env.py` | 生成上述三个键，开发环境默认 `shared` / `0.125` |
| `deploy/cluster/check-parity.py` | 新增数值禁区规则与注入验证 |

验收：探针 Job 确认可见显存等于请求额度；引擎启动日志显示 `--gpu-memory-utilization 0.9`
生效；把 `ENGINE_GPU_UTILIZATION` 改成 0.125 后同一模板在开发机可用。

### 仍然成立的判断

显存预算不进仓库。无论采用哪种切分机制，数值都属于部署容量决定，应由环境配置提供，模板只
声明从哪个键取值。开发环境若与共享平台共用同一张卡，取值要按"留出大部分给他人"来定
（此前的 0.125 是按整卡 48 GB 推算的，若平台切分粒度不同，按实际额度换算）。

配套检查不变：提交树里的模板若出现写死的显存数值，判红。

## 七、开发环境能模拟到什么程度

形态与逐单元对照见[目标架构图](../architecture/target-architecture.svg)与
[ADR 0014](../decisions/0014-development-environment-isomorphism.md)。

两台开发机：MacBook 跑应用面与数据面，MegaCube 跑算力面并带真实 GPU。除 GPU 有无与
数据面实现以外，其余单元按生产基线部署，不按"开发用不上"裁剪。

| 维度 | 能否模拟 | 方式 |
| --- | --- | --- |
| 双中心逻辑 | 是 | 两套组件 + 一个可切换的写端点 |
| 异步复制与丢失窗口 | 是 | 主备两库，人为制造延迟与断链 |
| 切换与对账流程 | 部分 | 演练脚本：promote → 重连 → 全量观测 → 比对；跨中心真实 RTT 无法复现 |
| 引擎控制路径 | 是 | `PlatformRuntime` 的桩实现，跑通提交/观测/停止与对账 |
| GPU 真实执行 | 是（仅 B） | MegaCube 单卡真跑，额度由配置声明 |
| 平台侧 GPU 切分 | 否 | 开发机是裸卡，不经智算平台 |
| 实时链路 | 否 | 入口尚未实现，两台机器都不部署 |

结论：开发环境能验证"切换后是否正确收敛"，不能验证"切换有多快、平台是否配合"。
后者只能靠平台联调与演练本身取证；在验收材料里不按已覆盖计。

## 八、改造顺序

| 顺序 | 事项 | 验收 |
| --- | --- | --- |
| 1 | 写端点单一定义 + 可切换 | 改一处即完成切换，无残留连接 |
| 2 | 切换演练（供应方 promote + 我们重连） | 演练一次：重连、对账、恢复准入；不自己写 promote |

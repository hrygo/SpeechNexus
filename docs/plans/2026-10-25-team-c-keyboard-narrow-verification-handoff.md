# 团队 C 交接：书籍页表单的真实键盘与窄屏核查（含焦点回落修正）

消费者清点归零后，本轮转向**C 侧可达的真实验证深度**：新增表单此前只有"鼠标/程序化填入"的证据，键盘与窄屏从未在真实浏览器里核过。

## 核查先暴露了一个真实缺陷

两个新表单在**成功后清空输入**，而提交按钮的禁用条件是"字段为空"——于是成功后按钮变禁用，**键盘焦点掉回 document**（`body`），键盘用户的下一个 Tab 从页面顶部重新开始。这是"清空表单"这种常见写法自带的焦点丢失，不是夹具问题。

修正：成功后把焦点**有意识**地移回该表单的第一个字段（单元表单→"新单元序号"，改名表单→"新项目名称"）。提交刚发生，焦点移动可预期，不会造成意外跳转。

## 真实浏览器核查内容（生产包 + 真实组合根 + 隔离 PG）

1. **只用键盘创建第二个单元**：依次填入 7 个字段，每个字段之间按 **Tab** 并断言焦点落到**下一个具名控件**（`toHaveAccessibleName` 直接读可访问名，验证真实的 Tab 顺序而不是"能被程序化设置"），再 Tab 到提交按钮并 **Enter** 提交；随后断言新单元出现、且焦点回到"新单元序号"。
2. **360px 窄屏**：断言 `scrollWidth - clientWidth == 0`（无横向滚动），并留档截图。
3. 既有断言全部保留（建书/建章节/建单元/音色修订拒绝/旧修订改名 409）。

## 两次过程修正

- 我插入的键盘校验块用了 `const values`，与探针既有的 `values` 同作用域冲突，Node 报 `Cannot access 'values' before initialization`（TDZ）——在校验代码里撞名同样致命；改名 `keyboardValues`/`keyboardFields` 解决。
- 我预期单元列表按序号升序，实测**先返回键盘创建的那个**；列表顺序属部署方，改为按集合比较而不是钉死顺序（钉住顺序会把部署方的合理实现当成失败）。

## 未验证与边界

- 键盘核查覆盖**书籍页新增表单**，不等于全站无障碍合格；读屏（VoiceOver/NVDA）仍未实测——需要 B 的目标环境与真实协助技术。
- 只测了 360px 一档宽度；触控、200% 缩放、高对比模式未测。
- 焦点回落是"回第一个字段"，未做焦点**陷阱**检测（Tab 是否会跑出表单）或 `aria-live` 播报核查。
- 浏览器证据来自 macOS + 本机 Chromium，不代表 Linux 后端或目标拓扑资格。

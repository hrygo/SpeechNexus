## 结论

**通过，建议合并。** 维护者（我）批它的那条硬条件成立：`unreplayable` 只在「本次意图此前没有任何
未观测尝试」时写入，且**我没有找到任何能让它在同键已有 Job 的情况下被写入的路径**。

- 缺陷已修：首次答复即 413 时用户获得显式出路（放弃并换新键），reload 后仍是「作废」而不是「结果
  未知」，且文案不声称「未执行」——这正是记录语义要求的三件事，三者都在新记录里成立。
- 修复没有放宽任何旧的保守性：`settlesReplayedIntent` 一字未改（函数体 md5 与基线相同），

  写入失败、随后重试才真正发出唯一一次 create 并得到 413 时，页面仍判「此前已有提交尝试」而拒绝给出
  出路。该情形方向安全（回到本 PR 之前的状态，不会重复执行），且需要一个反常前提（会话存储写入失败），
  因此**不阻断合并**；我已验证一个 3 行候选修法可关闭它且 869 条用例全绿（见「必须修清单」M1）。

## 本卡核心：`#record === null` 判据的假阴性 / 假阳性可达性

判据本体：`file-task-session.ts:946` 在 `#submit` 入口读 `const firstCreateAttempt = this.#record === null;`，
`:983` 写 `this.#createAttemptIsFirst = firstCreateAttempt;`，`:660` 的 413 分支以 `if (!this.#createAttemptIsFirst)`
保留 unknown。等价性论证依赖两点：**每条 create 请求之前都会先 `#persist({ pending: "create" })`**，
且**恢复的 upload 记录不进 `#record`**。

### 假阴性（把「没有尝试」误判为「有尝试」→ 用户被钉住）

| 构造 | 可达性 | 实测结论 |
| --- | --- | --- |
| 1. 记录因 upload 而存在（`pending:"upload"/"validation"`、含 `assetHintId` 的 v5），随后创建得 413 | **不可达** | 三种形状全部是「首次答复」：作废 + 可放弃 + 持久 `settled:"unreplayable"`，`create` 只发一次。作者那句「恢复的 upload 记录从不携带 create 请求」**核实为真**：构造器 `:333` 把 v1/v2 写 `#record`、v3–v6 写 `#upload`，upload 记录在结构上不可能占据 `#record` |
| 2. 记录因上一次 create 已 settled 而未 `clearCompleted()` | **不可达** | 不是「413 被当作非首答」，而是**新的 create 根本发不出去**：`#submit`、`continueAfterValidation`、`start`（`#model` 已定）全部早退，实测 `create` 调用数 **0**，页面停在「可放弃」，放弃后才换键 |
| 3. 记录存在但那次 create 从未真正发出 | **可达**（两型） | (a) **崩溃窗口型**：持久 `pending:"create"` 无 settled —— 与「已发出、响应丢失」的持久形状**逐字节相同**，纯状态判据无法区分，实测保持 unknown（这是设计上接受的保守方向）；(b) **首次 persist 失败型**：`#record` 在 `#persist` **之前**就已在内存赋值（`:972`），`#persist` 抛错后内存记录留下；重试时 `#record !== null` → 判为非首答 → 实测唯一的 create 请求（就是那次 413）被判「此前已有提交尝试」，`unknown:true / canReplay:true / canFinishTask:false`、无 `settled`、reload 后同样被钉住 |

第 3(b) 型是本次唯一实测构造成功的假阴性，触发条件是 `sessionStorage.setItem` 失败一次
（`SessionTaskJournal.save` 抛 `unavailable`）后恢复。判定：**方向安全**（只会「少给一条出路」，
绝不会「在没有尝试时允许放弃换键」），且完全回到本 PR 之前的体验，因此不构成安全缺陷；但它确实
落在「本卡要解决的钉死」这一类里，已在 M1 给出已验证的修法。

### 假阳性（把「有尝试」误判为「没有尝试」→ 清掉未知态、允许重复执行）

**不可达。** 论证是结构性的，不依赖新增字段：

1. `#createKey` 的两个来源：`saved === null` 时新铸 UUID（新键不可能已有 Job）；`saved` 是 upload
   记录时沿用其 `createKey`。
2. 沿用 `createKey` 的那条路要求该键曾随 create 请求发出，而 create 请求**必定**先写一份 v1/v2
   create 记录到 journal（`#persist` 在 `#client.create` 之前，且 `#persist` 抛错就发不出去）；一旦写过，
   `SessionTaskJournal.save` 既不允许回退成 upload 记录（`before && afterUpload → changed`），也不允许
   丢掉 create 记录，因此「键已用过但 `#record === null`」无法同时成立。
3. 唯一能把 `#record` 变回 null 的操作是 Host 的显式放弃，而它被 `canFinishTask` 门禁（要求
   `!unknown`）挡在未知态之外，并且放弃后 `initialize` 重建会话会铸新键。

实测反例搜索：同一次会话里先成功建 Job（键 K 已用）→ 手工删掉恢复记录 → 新会话对同一 413 走首次
分支，新键 `ee40cf8b-…` ≠ 旧键 `753c364a-…`，作废只落在新键上，不会碰到旧 Job。**未找到反例。**

### 结论

判据在本客户端能表达的所有正常路径上等价；不等价的唯一实测缺口是 3(b)（persist 失败后的内存残留），
它落在「漏给出口」一侧，不落在「重复执行」一侧。**维护者那条硬条件：满足。**

## A 组逐条

### A1 判据等价性

见上节表格，三种构造与反向构造都实测过。补充两点方法学说明：

- 探针没有复用作者的 `setup()`，而是自建传输层（upload / asset / create / job 四条路由）与
  存储注入点，记录形状则用真实 journal 读回校验（`load()` 通过即形状合法），因此「记录存在」这件事
  是产品代码自己承认的，不是手工拼出的可疑 JSON。
- 「恢复的 upload 记录是否真的不进 `#record`」是这一条的关键，直接读构造器可证（`:332-334`），
  三种 upload 形状的实测与读码结论一致。

### A2 反向（记录不存在但同键 Job 已存在）

见上节「假阳性」。另核一处细节：`FileTaskHost.onNew` 先 `clearCompleted()` 再
`session.dispose()` 再 `initialize()`；顺序上「清理失败」会先抛错、旧会话保持存活，不会出现
「记录已清、键还留着」的中间态。

### A3 reload 后判据是否仍成立

**必须仍可放弃——成立。** 实测：首次 413 后 dispose，用同一 storage 重建会话 `restore()` 得到
`unknown:false / rejected:true / unreplayable:true / canReplay:false`、`canFinishTask === true`，
notice 为「已找到原任务身份；该请求因请求体超过本部署的接收上限被拒绝，原意图作废。」；
`replay()` 是空操作（`create` 计数不变）；模拟 Host 放弃（移除键）后新会话用新键（
`cf74680c-…` → `f145b45f-…`）成功提交。`#submit` 的早退条件已从 `=== "terminal"` 放宽为
`!== undefined`，两种 settled 都不会被重放。

### A4 `#createAttemptIsFirst` 可变实例字段

**当前不会串味。** 实测：让第一次 create 阻塞在传输层，同时在飞行中调用 `replay()` 与
`continueAfterValidation()`，两者都被 `#run` 的 `busy` 守卫吞掉（`create` 只发 1 次）；放行后
再重放则是非首次，不作废。原因：所有会发 create 的入口（`start`/`startText`/`replay`/
`continueAfterValidation`/`#resumeInput`）都经由 `#run`，串行化成立；而该字段的唯一读取点在
`:660` 的 413 分支，其前一行就是本次 create 请求，所以不存在「读到上一次尝试的值」。

**但字段生命周期偏宽**：它在 create 之后不再复位，目前靠「每条 create 路径都会在请求前重新赋值」
和「settled 记录会早退」两条间接性质兜住。属可持续性风险而非现状缺陷，见建议 S1。

## B 组逐条

### B5 旧 reader 的 `invalid` 路径是否 fail-closed

**成立，且我是在基线上亲手验的**：在 `/private/tmp/sn732`（`origin/main`）里用旧 reader 读
`settled:"unreplayable"` 记录，`SessionTaskJournal.load()` 抛 `TaskJournalError`（message
`task recovery storage invalid`），存储内容原样保留（`load()` 不写）；同一 reader 仍正常接受
`terminal`。Host 侧 `initialize()` 捕获后返回 `null`，组件只渲染
「恢复信息不可用。请修复浏览器存储后重新载入；本页已暂停提交，原记录未清除。」——没有会话实例，
因此**不可能被误读成 unknown，也不可能自动重放**，且记录不被删除。

代价评估：受影响场景只有「新版本写过 `unreplayable` → 又回退到旧版本」，表现为整页只读的
fail-closed 锁，而不是任何数据动作；`#707` 引入 `settled` 时支付过同样的代价。**可接受。**

### B6 单调性

实测 5 条迁移全部被 `journal.save` 拒绝（`unreplayable → terminal`、`terminal → unreplayable`、
`unreplayable → 无 verdict`、`unreplayable → 填 jobId`、`unreplayable → pending:"cancel"`），
且每次拒绝后磁盘上的值不变。6 种畸形形状被 `validRecord` 判 `invalid`
（`unreplayable` + cancel 意图 / + jobId / + operationId / + cursor / 值域外字符串 / pending:null 已定任务）。
**`unreplayable → terminal` 的降级与升级都不存在**：写路径被 monotonic 检查拒绝，读路径在
`#submit` 早退，两者叠加后没有可达的改值路径。

## D 组逐条

### D10 可达性声明

三个数字的构造法我复算通了：常量项 197 B（固定键名与引号）+ 每码点编码宽度 × 4096
（CJK 3 B、astral 4 B、U+0001 经 JSON 转义 6 B），4293/12485/16581/24773 与表内四行自洽。

**但我用真实生产客户端（`FileTaskSession` → `SpeechFileClient` → 生成客户端）实测的常量项是 228 B，
不是 197 B**，因此四个数字整体**偏小 31 B**：

| 正文形态 | PR 表 | 本次实测 |
| --- | --- | --- |
| 4096 ASCII | 4293 B | **4324 B** |
| 4096 CJK | 12485 B | **12516 B** |
| 4096 astral 码点 | 16581 B | **16612 B** |
| 4096 U+0001（最坏） | 24773 B | **24804 B** |
| 2048 astral（textarea `maxLength=4096` 的真实上限） | 未列 | **8420 B** |

结论方向不变（最坏 24804 B ≈ 262144 B 的 9.5%，默认部署仍不可达），但「真实 wire body」这类
可复现声明应写明取数用的 selection（`model`/`voice_id`/`profile_id`/`workspace_id` 的长度直接进入常量项），
否则第三方无法复算。另外「4096 astral 码点」这一行按 UI 不可达：`TtsTaskInput.tsx:63` 的
`maxLength={4096}` 数的是 UTF-16 码元，astral 只能到 2048 码点（8420 B），所以 UI 可达最坏值不是
16581 而是 24804（U+0001）。这属于表格精度问题，不改变「防御性正确出口」的定位。

「默认不可达」的定位**诚实**：`settings.py:174` 的 `job_receive_max_bytes` 默认 262144、
下界 `ge=1`，运维可以合法地把上限调到 1 B，所以「只有调低部署上限才可达」确实是可达条件的全部
（另一条是「旧上限下已发出 create、随后上限被调低」）。定位为「防御性正确出口、不是日常路径」成立。

## 建议（非阻断）

- **S1**：`#createAttemptIsFirst` 在 create 之后不复位。当前安全，但依赖「所有 create 路径都会在
  请求前重新赋值」这条隐式约定；建议在 413 分支消费后置回 `false`，或把「本 call 是否首答」改成
  `#run` 内部的局部量（如 M1 的 `#createEverIssued` 快照），让字段语义与所有权一致。
- **S2**：`#persist({settled:"unreplayable"})` 失败时页面仍显示「已作废、可放弃」，而持久记录仍是
  unknown；用户此时点放弃是安全的（首次答复），但**刷新**会退回 unknown 并重新被钉住。与 `terminal`
  同构（既有行为），但 `unreplayable` 下「放弃」是唯一出路，建议在 persist 失败时把 notice 补一句
  「若刷新后回到未确认，请改用新的幂等键新建前先核对服务端」，或让面板文案不再承诺「刷新后仍保持作废」
  （`FileTaskPanel.tsx:104-108` 与 `:98-102` 都做了这类绝对承诺）。
- **S3**：`#run` 的分支顺序里，`mutation && this.#upload && view.unknown && !view.asset`
  这条「上传未确认优先」的守卫在 unreplayable 分支**之前**。当前不可达（`#persist` 在 create 之前把
  `#upload` 置空），但它是一条「靠顺序保证不可达」的性质；若将来 create 路径不再写 `#persist`，
  413 会被这条守卫吞掉。建议在 413 分支加一行注释说明这个前置依赖。

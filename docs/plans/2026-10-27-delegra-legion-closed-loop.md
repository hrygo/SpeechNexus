# Delegra 军团精简与真实闭环整改

本计划落实已授权的最佳方案与文档整改，记录控制权、配置核验和闭环退出条件，不另建产品 backlog。当前是**基础设施整改阶段**；底座修复、运行配置审定、平台应用、七岗准入、指挥权切换及首轮业务闭环分别验收，不能从文档完成推断后续已通过。

公开代码 / 契约以仓库当前主干为权威，产品范围与 AC 保留在 [#6](https://github.com/hrygo/SpeechNexus/issues/6)及对应 issue；执行与配置事实以当前平台回执为准。旧项目及任务已移除，历史编号仅作交接线索。[旧环境报告](../operations/paperclip/environment-readiness.md)继续保存原失败和未验事实。

## 采用的结构与切换

采用[军团工作流](../operations/paperclip.md)：基础设施整改及准入后，由本次整改会话转任部署记录中唯一 SM+PO，直接对 A / B / QA 及按需 C 派工。原技术协调岗改为按需集成助手；MiMo、证据岗按需调用。原产品总控会话改为按需独立架构 / 风险审查与备用接管，不保留另一条产品队列或自动巡检。

这项选择减少产品总控、常设技术经理和实施者之间的重复拆解 / 报告交接。另一方案是保留原 SM+PO、由整改会话移交退出，但需要额外交接本轮底座 / 配置事实，且常设中间调度在当前规模下仍重复维护队列。本轮未取得运行吞吐 / 成本数据，不宣称精简已改善性能或费用。

唯一 SM+PO 决定产品价值、优先级、范围、AC 和执行排序；常规产品实现、成员排障交具名成员。用户保留重大范围决定和最终 Gate / 投产放行。原会话和平台岗位不因 Sol 模型、PM 头衔或组织汇报关系获得第二决策权。私有部署 overlay 记录精确映射，公开源不保存私有会话 / 平台 UUID、机器私有路径、内部入口或秘密。

切换回执须包括：底座修复固定版本、已验 / 未验能力、唯一决策方和按需独审映射、唯一队列、当前活动任务及接收人。两个会话的 goal 应同步表达新职责；未明确切换前不声称已接管产品派工。角色源可提前部署，但其阶段条款不能自动启动任务。

## 七岗配置逐项核验

下表是审计读取和部署方脱敏配置回执提供的写前基线，**不是新配置已应用或模型任务资格通过**。当前授权允许依逐岗验证调整 model / effort，记录理由、前值与回读；不得通过更换连接绕过预算或内容网络边界。每岗核对实际字段、能力 catalog、有效执行环境、权限和运行结果。字段缺失、未支持与已通过必须分别记录。

| 岗位 / 预期用途 | 当前配置 model ID | Harness / 主机安排 | 思考配置字段与待核验值 |
| --- | --- | --- | --- |
| 原经理 → 按需集成助手 | `gpt-6.1-sol` | Native Runner / 本机 | Codex `modelReasoningEffort=xhigh` |
| A 主开发 / 集成 | `gpt-6.1-sol` | Native Runner / 本机 | Codex `modelReasoningEffort=high` |
| B 执行 / GPU | `gpt-6.1-sol` | Legacy Codex CLI / MegaCube | Codex `modelReasoningEffort=high` |
| QA 独立消费者 | `opencode-go-ds-flash` | Legacy Codex CLI / MacBook | Codex `modelReasoningEffort=high`；Harness 不使它成为 Sol reviewer |
| C 工作台专家 | `opencode-go-ds-flash(max)` | Claude Code / 本机 | Claude `effort` 尚无显式值；代理支持 model 后缀 `(max)` 且优先于 body，须另核实际路由后的有效值，避免再补 `high` 形成双源 |
| MiMo 交叉审查 | `claude-fable-5-dd-orp-62omim-og-edocnepo` | Claude Code / 本机 | Claude `effort` 尚无显式值；建议显式 `high` 后单独探测，未应用 / 未验，不由别名推断资格 |
| 证据与文档 | `paperclip/omlx-sage-a1.5` | OpenCode / 本机 | 未有受支持通用 reasoning 字段则记 `N/A`，不写假值 |

模型 ID 是当前配置标识，不等于底层模型身份或质量已独立验证。Codex 的实际 `modelReasoningEffort`、Claude 的 `effort` 与 OpenCode 支持字段须按对应 Harness 核对；通用 API 投影字段不能代替最终有效配置。catalog 可能是静态列表或未知模型的默认规则，未包含自定义别名不等于连接拒绝，列出 effort 也不证明下游接受。已获授权的修正依据实际协议、连接和验证结果进行，不为消除列表差异更换可用别名。

2026-10-27 只读核验：固定 Claude Code 2.1.310 的 CLI 支持 `--effort`，两岗 `engine=cli` 仅读取显式 `effort`；现有值均缺省，不能从别名推断真实底层模型。运行中的 CLIProxyAPI 二进制为 `1.3.4-upstream8.0.35` / commit `c3d0fc6b`，进程映射与固定二进制版本一致；该提交源码识别 `(max)` 并让后缀优先于 body。这证明运行版本具备后缀处理能力，仍不证明 C 的具体路由最终发出或上游执行了 `max`。本机代理源码本身不构成运行版本证明；版本 / 进程 / 同提交核对回执留在私有部署记录，最终值还需对应请求的脱敏翻译元数据。证据岗的 native OpenCode 未暴露通用 effort；CLI 的 provider-specific `--variant` 不能直接套入当前 MCP 字段。

同提交的未知 / user-defined 模型分支会接受后缀 canonical level，并交给目标协议 applier：Claude 写 `thinking.type=adaptive` 与 `output_config.effort`，OpenAI / Responses 写对应 reasoning 字段，由上游验证；该分支本身不因未知别名就降成 `high`。已知能力元数据则可能转换为 budget、按跨协议能力夹取支持级别、拒绝不支持值，或对明确不支持 thinking 的模型清除相关配置。因此 C 保留 `(max)` 单一控制源，不额外补 `effort`；MiMo 无后缀，建议显式 `high` 后再探测。不读取代理请求正文或秘密来追证，现有脱敏回执不含最终 effort 时如实保留限制。

权限也须逐岗核验。部署方回执显示：A 有 `canCreateAgents/canCreateSkills=true`；原经理、B、C、QA、证据岗有 `canAssignTasks=true`，MiMo 为 false。唯一派工结构不需要专家自行创建组织对象或第二队列，应审定本项目实际所需权限并通过受支持入口处理；这些是公司级字段，先核对其他项目 / 既有任务影响，不一刀切清除或把角色正文当权限实施。

2026-10-27 应用进展（与上述写前基线分列）：七岗均已通过受支持 API 关闭自行派工和创建 agent / skill 的权限，保留原模型连接及全部选中 skills。MiMo 已显式应用 `effort=high` 并通过对应连接的 CLI hello；C 保留 `(max)` 单一控制源，最终上游 effort 仍未取得回执。证据岗将 OpenCode 工具权限从 `allow` 收紧为 `ask`，尚待真实请求 / 处理生命周期验收。C / MiMo 的 typed 权限配置仍等待新代码部署，不能据源码已实现宣称 live 生效。

B / QA 的真实 Legacy 启动记录分别核到 Sol / DS Flash 及 `model_reasoning_effort=high`，主机、私有 Codex 入口和隔离 HEAD 一致。宿主已取得合成制品并校验字节；B 收尾遇到缺失 auth 文件的 SSH 错误契约缺陷，QA 因项目未定价用量门禁被取消，均未判完整准入通过。已启动 managed 远端 HOME / XDG 投影和 SSH 缺文件契约修复，不修改价格、放宽权限或重做制品以掩盖失败。全部岗位的工具 / 报告 / 收尾及首个产品切片仍待验收。

## 源、overlay 与发布接收

公开编译输入为 [common.md](../operations/paperclip/roles/common.md)和每岗聚焦正文；公司编排 skill 应同步职责模型。每岗 runtime 编译只携带必要共同边界与聚焦职责，不强制加载整本管理手册、所有角色或全部 skills。私有 overlay 只补实际身份 / 环境 / 准入映射，不扩大任务目标、权限或预算。

部署 manifest 分别记录：源提交与逐文件 SHA-256、overlay revision / hash、编译规则版本、各岗输出 hash、平台写前值及写后回读结果。角色正文用 `baseRevision` / hash、skill 用 `expectedVersion` 做受支持的 CAS；普通配置、model 和项目字段没有 CAS，串行写并保存前值、回读验证，不声称跨字段原子。写前重读；冲突先核实并行意图。公开源与编译正文裸 hash 不同是可预期结果，不能因此覆盖已确认的新运行指令。

B / QA 保留 Legacy CLI，依据是历史 native SSH 空 workspace 及远端 commit 回收索引未验；不得只为统一名字升级。新能力必须取得实际工作区、工具访问、固定修改 / 新文件回传、宿主接收和 finalize 证据。模型连接、管理员 SSH 自检或字段保存不代验这一层。

## 首轮真实闭环候选与退出条件

首轮候选是 [#30](https://github.com/hrygo/SpeechNexus/issues/30) / [#142](https://github.com/hrygo/SpeechNexus/issues/142) 的 TTS 请求音频硬上限传播修复。该切片已有本用户 goal 的实施授权且持续有效；底座修复和所需岗位 / 资源准入后推进，无需再次确认。当前尚非已启动产品任务，也不由本计划独立重排完整产品目标；其他产品范围和投产放行不因此扩权。

建议 B 为唯一实现者，A 为非作者 Sol reviewer；QA 根据最终候选和可运行接口独立验证适用消费者 / 故障场景。必要的补丁接入由具名集成写者承担，不固定唤醒集成助手、MiMo、C 或证据岗。独审与 QA 不能由作者换角色代签。

候选应验证请求 / binding / 实际 policy、源样本 / PCM 与编码制品上界，恰好上限 / 超一帧、较紧请求、固定身份重放及失败不发布。真实 GPU 验证按固定模型 / 镜像 / generation 与获准窗口，通过命令 / 默认工厂执行路径取证；adapter 冒烟不代验命令传播。停止 / 资源释放和预算事实分别证明，unknown 不退预算。

本轮管理闭环验收：任务准入 → 实际正确 checkout / 工具 → 固定候选 / 原始证据 → 报告持久保存并回读 → 修改回传与接收方 hash 核验 → 非作者审查 → 真实 GPU / 适用独验 → 最终候选复核 → 原生 finish / finalize → 按授权 PR / 集成与状态同步。各环报告通过 / 失败 / 跳过 / `not_run`，仅修复原因或输入改变后重试。

这不关闭完整公开 ASR / TTS 链、原工作包、模型质量、单请求释放、物理集群或 Gate；它们仍按各自原 AC 独立验收。没有实跑数据不宣称军团吞吐 / 费用改善；首三个切片可复用既有时间戳观察就绪至评审、等待、返工和缺失证据，不新增自动化或第二统计队列。

# 0002：语音模型、推理引擎与加载策略

## 背景

语音底座同时包含文件与实时 ASR、预设音色合成、音色设计、样本克隆、对齐、VAD 和匿名分人。只确定 ASR / TTS 家族不足以指导部署：不同 checkpoint 承担不同能力，音色创作还涉及多阶段预算、可复用资产和实例加载策略。

本决定记录 2026-10-22 逐项确认的首选验证路径。`accepted` 仅表示选型和治理方向已接受，不表示机器契约冻结、适配器已实现、目标主机可运行或生产资格通过；当前没有本组合的真实推理、质量、容量、取消或长时稳定性证据，也没有足够证据宣称它是所有场景的最佳组合。

## 决定

### 1. 模型与推理引擎

| 能力 | 首选模型 / 制品 | 首选推理引擎 |
| --- | --- | --- |
| 文件 ASR / 完整段复核 | `Qwen/Qwen3-ASR-1.7B` | vLLM |
| 实时 ASR | `Qwen/Qwen3-ASR-0.6B` | vLLM |
| 预设音色合成 | `Qwen/Qwen3-TTS-12Hz-1.7B-CustomVoice` | vLLM-Omni |
| 描述式音色设计 | `Qwen/Qwen3-TTS-12Hz-1.7B-VoiceDesign` | vLLM-Omni |
| 样本克隆 / 创作音色的后续复用合成 | `Qwen/Qwen3-TTS-12Hz-1.7B-Base` | vLLM-Omni |
| VAD | 官方 Silero VAD ONNX 制品 | ONNX Runtime CPU |
| 强制对齐 | `Qwen/Qwen3-ForcedAligner-0.6B` | 官方 `qwen_asr` / PyTorch CUDA 路径，底层依赖 Transformers |
| 匿名分人（说话人分段与标注） | `nvidia/Nemotron-3-Diarization` | NeMo / PyTorch CUDA |

选择依据与约束：

- ASR 分开验证轻量实时路径与较大模型的文件 / 完整段复核路径；模型大小本身不能证明延迟或准确率达标。预览、复核和最终正文的修订规则仍由 SpeechNexus 契约负责。
- CustomVoice、VoiceDesign、Base 分别承担预设音色、描述设计和参考音频克隆，不把同一实例视为全部能力的实现。TTS tokenizer / codec 随运行时和完整阶段图锁定，不另列为业务模型选型。
- VAD、对齐和分人使用独立辅助运行时，按同一资源治理规则执行，无须强行经 vLLM。内部模型采样率转换保留与公共 canonical 音频时间轴的映射，不改变公共音频坐标。
- 分人首轮验证覆盖实时与离线、最多八位说话人的范围；跨块标签连续性、重叠语音和复位行为需要实测。更大人数的后端尚未选择，pyannote 未进入本次选型。

模型与引擎的角色依据见本文末尾的上游来源；具体版本和运行能力以目标部署资格记录为准。

### 2. 常驻与按需加载

| 实例 / 用途 | 加载与资源要求 |
| --- | --- |
| 已启用的实时 ASR | 预加载、热身并就绪后才准入，服务期间保持常驻 |
| 承担实时合成的 CustomVoice / Base | 对已启用的绑定预加载、热身并常驻；不因 Base 也用于克隆而按每次合成冷启动 |
| VoiceDesign | 随音色创作任务按需加载；无在途工作且满足部署空闲回收策略后卸载 |
| 克隆 / 复用校验 | 优先在受控音色创作预算内复用已就绪 Base；不能挤占实时保留或绕过队列 |
| VAD | CPU 常驻，模型可共享，会话推理状态隔离 |
| 文件与其他辅助绑定 | 由部署资格分别确定，不从上述规则推断全部常驻或全部按需 |

使用预先准备并锁定的本地权重；推理和音色创作请求不触发权重下载。空闲时限、排队边界与加载超时在后续部署策略及机器契约中定义，本 ADR 不新增默认值、配置字段或错误码。

### 3. 自动协调与部署控制边界

平台根据任务需求、实例可用性和资源预算自动协调准备与回收。实际模型进程 / 容器的启停由受限部署侧控制器通过 Compose 或运维基础设施执行；不是逐个任务人工启动，也不在 FastAPI 业务进程中加载大模型。

调度器先原子预留加载、热身和完整模型阶段的峰值资源，再请求控制器启动；不能只按稳态权重大小估算，也不能依赖资源不足后再驱逐实时模型。预算不足时音色创作排队，不借用实时保留。共享物理内存的部署由父预算统一核算，不能将同一资源分别计为主机和设备的独立余量。

执行网关继续独占推理入口和引擎凭据，拥有提交 fencing、abort 与完成证据。部署控制器只拥有受限实例生命周期操作；业务 API、worker 和工作台不能因此获得直接引擎访问或任意容器管理能力。

回收前先停止新分派，协调在途执行并 drain，再由控制器停止实例。只有确认在途执行结束、实例停止且资源释放后才归还实例预算；启动、取消或停止结果未知时继续隔离并占用相关预算。任务增量预算与实例常驻预算分别记账，任务完成不等于模型内存已释放。详细不变量由[资源治理](../architecture/runtime-governance.md#16-按需加载与实例回收)维护。

卸载不退役绑定，也不删除音色资产、来源、版本或校验证据；再次加载必须重新核对实例 readiness。资格仍须与实际模型、引擎、配置和部署组合匹配。

### 4. 音色创作的完整闭环

描述设计采用以下路径：

```text
描述 → VoiceDesign 候选 / 参考音频
     → Base 克隆与复用校验
     → 显式发布不可变 VoiceRevision
     → 后续由 Base 合成
```

样本克隆从明确提交的参考材料进入 Base 路径。生成、修改后再生成、试听、校验、发布，以及退役 / 禁用 / 删除依赖，均属于音色创作验收范围。只有试听产物的候选保持 `preview_only`，不能据此发布可复用声音。

音色资产与校验证据独立于实例存活保存，发布必须关联兼容的绑定 revision。流式输出、参考材料复用和跨模型兼容分别验证；不能从“生成了一段音频”推断后续复用、换文合成或流式能力已经可用。公共音色语义仍由[语音接口](../architecture/speech-api.md#17-音色创作与增强协议)负责。

### 5. 首轮部署与验收

首个验证目标为当前 Linux ARM64 / NVIDIA GB10 主机；硬件、内存拓扑和驱动事实属于部署资格记录，不进入公共 API 语义。已有主机观察不能证明可用推理内存或容器兼容。

最低混合负载为同时运行 **1 路实时 ASR + 1 路实时 TTS**，首轮验收要求为：

| 指标 | 已确认的首轮要求 |
| --- | --- |
| ASR 首预览 | 满足最低识别窗且对应音频进入服务后，首个有效预览 P95 ≤1000 ms |
| TTS 首音频 | 冻结文本获接受到首可播放 PCM，P95 ≤800 ms；网络与播放单独报告 |

验收还应覆盖 VoiceDesign 冷加载、热身、执行和回收与实时负载共存时的影响；资源不足须受控排队。完整音色创作闭环必须独立验收，不能由上述 1+1 性能测试替代。更高并发、文件吞吐和各辅助服务容量按实测写入 CapacityManifest。

进入真实引擎验证前，仍须锁定并记录：

- 模型 revision / 摘要、精度及 tokenizer / codec 制品；
- 引擎版本、容器摘要、独立推理依赖，以及 ARM64 / GB10、CUDA、PyTorch、驱动和计算内核的匹配组合；
- 模型、运行时与第三方资产的许可证及使用条件；
- 拓扑、完整阶段资源峰值、实时保留、加载 / 回收策略和停止证据；
- 经授权语料、语言与场景、质量阈值、负载、延迟口径、取消 / 故障和长时验证结果。

应用与各推理运行时分别锁定依赖，不能要求所有 vendor 依赖进入应用的 Python workspace。上游支持列表、健康检查和成功启动均不能替代上述资格。

## 影响

- 首版有明确的验证顺序和 checkpoint 分工，适配器仍通过服务中立端口提供能力。
- 实时模型的常驻成本必须在部署准入前得到保障；VoiceDesign 节省空闲常驻资源，但增加冷启动、队列和生命周期协调工作。
- 部署自动化新增受限控制器职责；其操作与执行网关的提交、停止和容量事实必须一致。
- 本决定作出时公共业务契约尚未冻结；后续 P0 机器契约已交付，见 [contracts/README.md](../../contracts/README.md)。本决定本身不增加路由、状态枚举或可用能力声明，也不修改外部运行态。
- 若目标主机的兼容性、质量或混合负载不达标，应依据证据修订选型或部署方案，再更新 ADR 与绑定资格。

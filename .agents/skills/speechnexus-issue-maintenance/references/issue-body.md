# Issue 正文规范

供 issue 日常维护与合并后同步共同引用；状态判定由相应工作流处理。本文件规定正文内容，不扩大远端写入授权。

## 四个独立部分

| 部分 | 内容 |
| --- | --- |
| `目标` | 要解决的问题、完整交付结果与必要范围边界 |
| `进展总结` | 已交付/已集成/已验证事实、仍缺实现或接入、关键风险、阻塞及解除条件；链接证据并明确未提交、未集成、待验证 |
| `任务清单` | 可执行、可勾选的实施步骤；已交付步骤须有依据，较大独立工作在授权内拆子 issue，未获创建授权时提出建议 |
| `验收标准（AC）` | 可观察的行为和结果，按风险覆盖正常、失败、边界、并发与恢复；保留阈值、版本和拓扑要求 |

任务与 AC 分开维护。任务勾选表示步骤完成，AC 勾选须有对应验收证据；PR 合并、绿色 CI、fake 或组件测试不自动完成业务行为或目标拓扑 AC。混合要求仅部分完成时保持未勾选，说明已完成与剩余范围；拆项时保留等价的全部要求。

使用“已交付……”“已集成……”“尚未接入……”“完成……后验收”等直接语态。事实不确定标待验证，不把编辑者描述或未经核实的完成声明写成现状。时效性结果注明核验日期（`Asia/Shanghai`）；合并日期与验证日期分别表达。

## 日常小 issue

默认一个边界清晰的问题由一个 PR 完整解决并关闭。四部分可以分别只有一句话或少量检查项；任务与 AC 仍分开，不为凑篇幅增加步骤。AC 只规定本问题所需的可观察结果和相关风险，不机械套用大型工作包的全部拓扑、质量或阶段要求。

实现和 AC 验证随该 PR 完成，合入主干后即可关闭；原要求已有额外验收条件时照常满足。问题确实跨多个 PR、模块交付或联合验收时才拆分，不为小 issue 创建父项、Gate 或中间状态。

## 层级与依赖

仅在存在相应关系时使用以下层级规则；独立小 issue 不展开这些流程。

- Epic 汇总阶段目标、子 issue、整体成果与退出条件；不复制全部子项清单。
- 工作包维护可执行步骤和完整行为 AC；阶段放行不意味着整包完成。
- Gate 汇集并核对联合证据，明确前置、上一 Gate 等要求与放行条件；子项关闭、单 PR 合并不自动放行。
- 通用完成要求集中引用；负责人、状态、优先级、父子关系使用 GitHub 可用字段。正文补充必要语义，不自行猜测字段 ID。
- 依赖写明所需接口、版本或具名制品；真正阻塞时写清负责人、影响和解除条件。其他路径能推进时不把关联引用一律设为整包阻塞。

## 保持当前摘要

每轮就地替换、合并与去重，不按 PR、日期或轮次增加平行章节、折叠历史和重复检查项。原有有效验收证据继续保留，当前失败、未决问题与阻塞不能被成功摘要覆盖。

同一结论保留当前有效的 PR、报告或证据索引；命令输出、测试明细、截图与 SHA 清单链接到已有来源，不转为反复追加的长评论。唯一验收证据无可靠外链时保留最小可追溯摘要；不因压缩丢失要求、证据或失败路径。

小 issue 的进展通常 1–2 条即可，较大事项通常 3–5 条，不凑条数。进展总结默认不超过 600 字符，完整正文默认不超过 6000 字符，统计包含 Markdown、链接与折叠区。写前比较新旧字符数；超预算或增长超过 10% 时先去重、合并和收敛证据。无新增授权范围或影响实施/验收的必要事实时，原则上不长于原文。预算用于发现堆积，不截断正文、删除 AC 或降低阈值；仍需超出时在交付中说明原因，不把统计写进 issue。

仅正文整理依据现有描述及其证据，保持元数据不变。发现矛盾保留未决事实并指出待澄清项；改变范围须有授权，并同时调整目标、任务与 AC。

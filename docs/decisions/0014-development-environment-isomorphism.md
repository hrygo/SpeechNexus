# ADR 0014 开发环境同构与允许的差异边界

## 背景

开发环境长期按"能跑起来"取舍，结果两台机器各跑一半：MacBook 跑应用面与数据面，
MegaCube 跑执行网关、节点控制器与引擎，中间用 `bridge`（SSH 隧道）缝合。
这个形态能工作，但它验证的是一条生产上不存在的路径——生产里业务单元、网关和控制器
在同一个中心内，从不经手写隧道互相调用。

[ADR 0011](0011-distributed-deployment-and-platform-boundaries.md) 已确认分布式部署是目标、
单节点是验证拓扑，但没说清开发环境应当部署到什么程度。用户 2026-11-21 明确要求：
**开发要尽量同构模拟，尤其是无状态应用和对内存、显存需求不大的应用。**

核实当前状态（2026-11-21，`kubectl -n speechnexus get pods` 与 MegaCube 实机）：

| 单元 | MacBook | MegaCube |
| --- | --- | --- |
| 入口代理、Speech API、Workbench API、asset-inspector、后台 worker | 运行 | 不部署 |
| Execution Gateway、Node Controller | 不部署（经隧道借用） | 运行 |
| 推理引擎 | 无法运行（无 GPU） | 运行 |

## 决定

1. **开发环境以生产部署单元集合为基线。** 默认部署单元清单与生产一致，不按"开发环境
   用不上"裁剪。省略一个单元，就少一条被验证过的路径。
2. **允许的差异只有两类。** 一是数据面实现（自建 PostgreSQL / MinIO 代替 SaaS），
   二是 GPU 有无（MacBook 没有 NVIDIA GPU）。其他差异视为缺陷，不视为设计。
3. **同构缺口必须显式标注。** 尚未在本地部署的单元用虚线槽位与 ⊙ 标记，
   不得用实线画成已运行；验证不了的项（实时链路、中心级切换）在文档中声明为不可验证。
4. **两台机器都是开发环境，不分主次。** 不设"主开发机"，也不把某一台当作另一台的依赖。
5. **隧道不是同构的替代品。** `bridge` 只承载跨机 TCP 通路，作用是内网 TLS 的开发期
   替身；它不构成状态边界，也不能用来说明某个单元"已经同构"。
6. **同构度可核对。** 维护逐单元的同构矩阵（● 同构运行 / ⊙ 目标同构未部署 /
   ◐ 实现不同 / ○ 不运行），作为开发环境变更时的检查依据。

## 后果

- 需要通过把执行网关与节点控制器各部署一份到 MacBook 来消除主要缺口（本轮待补）。
- `bridge` 的用途收窄为数据面回连；引擎成为 Pod 后可整体删除。
- 开发环境新增单元时，先问"生产有没有"，而不是"这里需不需要"。
- 同构矩阵成为文档的一部分（见[部署单元与平台规划](../architecture/deployment-units.md)
  与[目标架构图](../architecture/target-architecture.svg)），变更时同步维护。

## 不在本决定范围

- 开发环境的具体编排方式（k3s、Docker Desktop k8s、Compose 各自承担哪部分）。
- GPU 显存额度如何声明，见 [ADR 0015](0015-gpu-memory-quota-by-configuration.md)。
- 生产的双中心形态与切换语义，见[双中心生产架构方案](../plans/2026-11-21-architecture-optimization.md)。

# PO / SM 运行手册：怎么带一支 Agent 团队持续交付

适用于**由多个 Agent 组成、通过任务卡与巡检脚本协作**的交付团队。补充[项目经理工作约定](project-manager-guide.md)，不扩大其授权范围；可提交、合并、派工、改运行态的边界仍以根[工作约定](../AGENTS.md)为准。

当前产品范围以[总控 #336](https://github.com/hrygo/SpeechNexus/issues/336)及[完整矩阵](plans/delivery-tracking.md)为入口。本页用于推进已授权切片的交付、验收与恢复；空闲 Agent 不构成派工理由。

## 0. 一句话版本

> 核对当前目标与输入 → 推进具名切片 → 固定产物并验收 → 收尾工作区 → 留下接续事件。

派工不是"发出去就算"，**以实际启动确认派工，以实际产物确认进展，以验收证据确认交付**。

## 1. 需要核查军团执行时读取面板

先看当前 issue、固定候选和已知阻塞；只有需要派工、诊断执行状态或收尾时才读取面板，不为等待重复巡检。

```bash
scripts/dev-env/fleet-status.sh          # 人看
scripts/dev-env/fleet-status.sh --json   # 脚本/CI 消费
```

单次运行的退出码通常为 `0` 无事项 / `1` 有事要动 / `2` 面板不可用或调用无效（如缺 `psql`、连接或主要查询失败、多公司未指定 `--company`、无效的 `--watch` 值或未知参数）。未指派的 `in_review` 计数查询失败时，脚本会按 `0` 处理，可能漏报；需要裁决时应另行核实。`--watch` 会持续刷新，不提供单次结果的退出码；`--json` 的输出不包含该未指派计数，虽然退出码会计入它。

面板把 Agent 分成可操作的几类：

| 面板标记 | 含义 | 动作 |
|---|---|---|
| `有活没动` | 空闲，但名下有 `todo`/`in_progress` 卡 | 核对运行、排队、任务状态和唤醒记录，不能仅凭面板断定唤醒失败 |
| `可派活` | 空闲且无在办卡 | 仅在已授权切片输入就绪、无写冲突且资源允许时派工 |
| `超时` | `running` 超过面板阈值 | 核对进程、近期输出及产物；运行时间较长不等于卡死 |
| `唤醒异常` | 近期有 `deferred`/`failed` 唤醒 | 查 `reason` 再处置 |
| `N办/M审/K停` | 在办 / 待裁 / 停放（`backlog`+`blocked`） | 停放不算没动 |

### 面板本身可能说谎，先核它

面板第一版把 `backlog`（有意停放）算进「有活没动」，一次误报 4 个正常 Agent。**判定错误的面板比没有面板更危险**：它会让你去修不存在的问题，或者忽略真的卡死。

迁移到新环境时，先拿一个已知状态的 Agent 做对照，确认三类状态（在办/待裁/停放）都落对位置，再信它的汇总。

### 面板测不出来的，靠人补

| 盲区 | 补法 |
|---|---|
| 跑着但跑错方向 | 看 `running` 时长 **+ 工作区有没有新改动**（`git status`） |
| `in_review` 但没有交付物 | 打开卡核对产物，不信状态 |
| Agent 自报比事实乐观 | 每条 AC 配一条可复现命令 |
| 唤醒被静默挡住 | 查唤醒记录里的 `status` 与 `reason` |

## 2. 唤醒失败：四种已确认模式与处置

Agent「显示空闲但不动」几乎都不是能力问题。按顺序排：

| 现象 | 真因 | 处置 |
|---|---|---|
| 空闲但名下有 `todo` 卡 | 可能是状态残留、排队或唤醒未完成 | 先核对状态、运行和唤醒记录，再按获准的管理流程处理 |
| 评论唤不醒 | 唤醒可能被 `deferred`，例如 `reason=decision_pending` | 核实待答问题与已有工作；解除条件满足后再安排续接，避免重复派工 |
| 同一 Agent 两张卡并发 | 会话协调失败（`persisted active turn`） | **一个 Agent 同时只给一张卡** |
| Agent 反复重跑已完成的卡 | 在 `in_review` 卡上反复评论，每条评论触发一次 run | 不在已完成的卡上评论；必要时取消排队 run |

原则：先核实执行状态和阻塞原因，再选择获准的恢复方式；保留已有成果，避免重复执行。

## 3. 用对照组诊断，不要猜

判断「这个 Agent 坏了」之前，拿一个正常 Agent 对照：比运行记录、配置、唤醒状态。曾有 Agent 被误改配置，回滚后证明**原配置一直是好的**，真正原因在外部连接。

没有对照组的"修复"很容易把好的改坏。

## 4. 任务切分：让每个任务都有可见产物

一条卡应提供可独立接收的产物、明确边界和必要证据：

- **验证缺陷**：逻辑修复用失败用例证明问题，再验证修复；纯文档按文档检查，不新增无收益测试。
- **回报关键变化**：固定候选、交接、实质阻塞和验收结论时更新原卡，不按每个步骤刷评论或重复唤醒。
- **说明阻塞**：给出缺少的输入、提供方与解除条件；继续同切片可独立完成的已授权工作，无工作可做时等待具体事件。
- **范围单一**：一卡一缺陷。范围宽的卡容易在 50 分钟里零改动。

判断任务是否卡住应结合进程或会话状态、近期输出、产物和等待的具体事件；运行时间或暂时没有新产物都不能单独证明卡住。

## 5. 按任务选择执行方式

按任务的独立性、判断复杂度和宿主能力选择执行方式；涉及代码与契约对照的文档审阅同样需要判断，不能仅按文件类型归为机械任务。确需委派时，明确范围、交付物、验证方法和文件写入归属，并按根工作约定选用代理。

路径和行号应通过工具及目标内容核实，不能凭推测补全。

## 6. 文档与引用的机器判据

```bash
scripts/dev-env/check-doc-refs.py            # 检查可识别的「文件:行号」引用
scripts/dev-env/release-preflight.sh          # 历史候选的局部上线前检查
```

上线前检查默认会访问配置的网关，部分检查固定了历史候选的假设；执行前应阅读[检查项与证据边界](operations/release-preflight.md)，并对照目标部署。默认跳过的检查不代表通过。

最终验收应按具体候选及授权范围执行；仓库当前没有 `scripts/dev-env/final-acceptance.sh`。

`check-doc-refs.py` 仅识别脚本列出的文件扩展名与 `路径:行号` 格式，以 Git 跟踪的文件定位目标，并将行内标注“外部依赖”的引用排除在问题之外；它不检查普通 Markdown 链接，也不能证明目标行就是文档所说的内容。仍须检查其他引用并打开目标行核对语义。

## 7. 验收：门禁必须会红

- 新写或修改的门禁应使用已知不满足条件的反例，确认能检出问题；正常输入首次运行通过并不能证明门禁无效；
- 收紧判据时用**反向对照**：把被检查的东西退回修复前，门禁必须重新变红；
- 门禁说谎的两个方向都要防：说"绿"（漏报）和说"更差"（误报）——**后者会让人去修不存在的问题**；
- 文档说"已可用"、门禁说 FAIL 时，**以门禁与实测为准**，并改文档。

## 8. 并发与共享资源红线

- 同一文件、同一 worktree、同一引擎/端口**不得两人同时写**；撞车先核归属，不覆盖、不回退他人改动；
- 已知会被多人改到的"热点文件"（门禁脚本、总入口文档、契约）**指定唯一写者**，其余人提需求；
- 派工前先看目标卡和工作区是否已被占用，再决定落点。
- 接管及派工前，按[工作区收尾](operations/agent-delivery-sop.md#工作区生命周期与收尾)复核原任务的临时检出与保留例外：交付负责人须同轮处理已结束资源，例外默认在 24 小时内复核；超期推进具名修复，不自动续期或强删。旧工作区处置未明确时不创建同一切片的新副本，无关独立工作可继续；面板空闲不能证明工作区已清理，不新增巡检任务。

## 9. 每轮结束时留下一件事

每轮必须留下**下次能被触发的依据**，否则这一轮的推进在下一轮就丢了：

- 依赖的具体事件（哪张卡完成、哪个 PR 合并、哪个人裁决）；
- 已配置的周期检查（若有）；
- 需要人工决策的事项，写清所需授权、影响和建议。

没有可用触发机制时，明确写出这个缺口，而不是假设"下次自然会想起来"。

## 10. 交接

用一页纸交接，包含：

- **当前目标**与判定它完成的标准；
- **关键路径**与主要交付缺口（按影响排序）；
- 每个 Agent 的**当前任务 + 下一项候选**；
- **阻塞清单**：解除条件、责任人、下一步动作；
- 本轮**已合并的 commit** 与仍未验证的结论（区分实测/文档/推断）。
- **工作区收尾**：已清理 / 不适用；保留时列对象、具名负责人、原因、成果位置、解除条件与下次复核时间。

不写流水账。"谁在什么时候改了什么"不如"现在是什么状态、下一步谁做什么"。

# CI 资源分组优化实施计划

> 使用 `writing-plans` 形成计划，按 `executing-plans` 在当前会话实施；结束时独立审查。

**目标：** 根据历史 Actions 数据减少重复准备与测试收集，保留完整集成验证；不触发托管 CI。

**设计：** 六个隔离数据库分片保持不变。有两类用例时，先按 Web 工具需求分组，再在组内使用稳定 SHA-256 分配；六片中四片承担普通数据库测试，两片承担浏览器与 Node 消费者。所有阶段复用同一个分组函数。

**技术：** Python 标准库、pytest、现有 GitHub Actions 工作流。

**依据：** [CI 规则](../architecture/ci-validation.md)、当前用户要求；历史样本为 2026-10-26 最近 12 次成功全量运行。

## 约束与审查重点

- 不触发、重跑、取消 CI，不提交、推送或改 GitHub 配置。
- 保持六组、10 分钟作业预算、完整双库/MinIO 执行、同提交全集并集检查及原受保护检查名。
- 不修改业务事务、数据库、模型、覆盖率统计范围或 80% 门槛。
- 单组、仅一种工具类别、参数化身份和输入顺序不能造成遗漏或重复。
- 预检、执行、汇总必须使用同一分配；错分、缺结果、失败和意外跳过继续拒绝。
- 少于六个分片的本地入口仍须能运行，不从固定分片编号推断工具需求。
- 历史推算不能表述为优化后的 runner 实测；新增用例时仍需检查工具分类。

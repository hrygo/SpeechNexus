# B01 恢复扫描公平轮转与互斥计数

开工基线 main `402d537b51f2e1ebec25257b57df9e51267e0b13`。
本轮处理 [PR #110 管理审查5638557709](https://github.com/hrygo/SpeechNexus/pull/110#pullrequestreview-5638557709)
仍开放的前缀饥饿、报告重复计数两项；共享停止证据 ID 已由 #114 修复，不重复实现。

## 反证与结果

旧实现每轮固定读取 `updated_at_us, submit_intent_id` 的前缀。最前面的记录长期无证据时，
下一页没有入口。新单元测试保留500条未知记录，第501条有完整证明；
两轮都只能读前500条，后续可关闭执行被饿死。真实 PG/InnoDB 用批大小1的两条记录
重现相同缺陷：第二轮仍检查第一条。

另一个真实并发场景在枚举结束后暂停扫描线程，由另一线程通过原生事务追加
100个 `GENERATED` PCM 样本；version 增加，状态仍 unknown。
旧实现同时增加 `observed` 与 `still_unknown`，有停止证明时则同时增加
`observed` 与 `closed`。两种情况都因分类和大于 `examined` 抛错；
有证明的路径甚至已提交停止事实才抛错。

修复前，3个新单元场景和6个 PG/InnoDB 参数场景按上述生产缺陷失败。
未通过删除断言、调整跳过或将用量写入改成直接篡改 version 来消除失败。
修复后保留这些反例，连同绕回、服务重建、来源失败、范围与重叠扫描的回归通过。

## 实现与契约边界

- 原生 `ExecutionRecoverySource.list_quarantined` 增加可选
  `after_submit_intent_id`，默认仍从头读取；PG、相同SQL的InnoDB测试装配及fake同时更新。
- 只读查询按不可变ID做严格递增keyset分页；服务保留本地访问游标，空页重置下一轮。
  游标前方的新记录在绕回后访问；有限集合中的未知前缀不再阻挡后续记录。
- 来源/写入失败时已访问ID不会永久钉住后续项，异常继续上抛；
  枚举本身失败则保留原游标。同一服务拒绝重叠调用，不排队。
- `observed`、`closed`、`still_unknown` 互斥。用量version变化本身不算状态观察；
  完整证明被原停止事务接受才算关闭，已追加样本保持完整。

不修改未知记录的时间/版本来调度，不新增持久游标、SQL函数、触发器、租约或预算权威。
分页复用普通比较、排序和LIMIT及既有列排序规则，不引入PG特有能力或迁移。
读取保留原期限/只读事务，网络观察与证明查询继续位于事务外。
公共HTTP、机器契约、生成器/生成物、锁文件、A事务与预算实现、部署和CI未改。

调用方必须复用一个服务实例。服务重建可重新读取旧未知项，但不依赖游标决定执行权、
释放或证据身份；回退旧代码不需要回退数据库，会恢复旧扫描缺陷，不能据此宣称修复有效。
这不是默认周期驱动的实现，也没有启动新后台线程。

## 本机验证

Linux ARM64、Python 3.14.9；仅使用项目隔离PG/InnoDB测试实例和合成数据。
PG采用生产网关适配器/最小角色，InnoDB执行同一SQL/领域规则的测试装配，
不声明生产MySQL adapter已交付。不加载模型、不使用私有录音、不操作GPU服务。

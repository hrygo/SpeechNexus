# 合并后同步 Issues

让相关 issue 准确反映主干已交付内容、实际验收结果和剩余工作。PR 合并只是集成事实，是否完成须按每张 issue 的完整范围判断。

## 入口与授权

- 在已授权的 PR 合并收尾，或用户明确要求同步已合并 PR 的相关 issue 时执行；已有授权覆盖的正文、状态与标签维护直接完成。单纯查询、审查或编写建议时仅给出核对结果与拟改内容。
- 本 skill 不授权合并其他 PR、变更需求或 AC、创建 issue/标签、调整负责人/父子关系、发布或操作业务运行态。遇到范围外事项，先完成已授权部分，再说明所需决定。
- 这是 Agent 执行的项目工作流；skill 文件不监听 GitHub 事件，也不自动安装 Action、webhook 或定时任务。
- 使用当前可用的 GitHub 连接器；其能力不足时使用已认证的原生 `gh`。不读取令牌、不新建鉴权配置；访问失败时报告未完成项。

## 项目依据

按需读取下列材料，远端现状须重新核实：

- [AGENTS.md](../../../AGENTS.md)：issue 四部分结构、证据与授权边界。
- [编排清单](../../../docs/plans/2026-10-23-implementation-issues.json)：定位工作包、Epic、Gate、总控和具名制品依赖；与当前原生关系不一致时报告差异，不自动改关系。
- [三团队方案 §12](../../../docs/plans/2026-10-23-three-team-delivery-plan.md)：分段交付与整包关闭的区别。
- [刷新工具](../../../scripts/dev-env/refresh-implementation-tracker.py)：现有状态词汇和矩阵生成入口；本地矩阵是快照，不是验收证据。

## 1. 固定合并事实和受影响范围

1. 核对目标仓库和 PR，读取远端仓库的默认分支或明确指定的项目主干，不从本地当前分支或名称猜测。确认 PR 已实际合并到该主干，记录 PR URL、base、合并时间和集成 commit。未合并、只关闭或合入其他分支时，不执行合并后的完成更新。
2. 读取 PR 正文、实际 diff、必要的审查结论与检查结果。分别标注检查对应的 revision、运行环境、通过/失败/跳过及覆盖范围；分支 CI 不能冒充合并后验证。发现交付已被后续回退或证据版本失效时，按当前有效事实判断。
3. 从原生关联、closing references、PR 正文及提交中的明确引用建立候选集。`Closes`/`Fixes` 是关联线索，不是 AC 通过证明。仅被顺带提及、背景参考或同名匹配的 issue 不写入；跨仓库引用先核对目标与授权。
4. 读取直接相关 issue 的最新正文、`state`/`state_reason`、标签、原生父子/阻塞关系，以及必要的评论和验收链接。再沿已确认的交付影响定位父 Epic、对应 Gate、总控和依赖该制品的 issue；只更新确实发生变化的部分，不遍历改写全部 issue。

为每张确认相关的 issue 建立简短核对表，可保留在工作上下文中，不必创建过程文件：

| Issue / 类型 | 关联依据 | 本次交付、任务与 AC 证据 | 剩余工作 / 真正阻塞 | 当前 → 目标状态及正文改动 |
| --- | --- | --- | --- | --- |

证据须对应具体任务或 AC，并能定位 PR、制品版本、检查运行或报告。历史勾选、PR 的完成声明、绿色 CI 和 issue 已关闭本身不能替代证据。证据不足时保留“待验证”，不补写成功结果。

## 2. 分别判定任务、AC 和状态

- 任务完成表示该步骤已交付；AC 通过表示对应可观察行为已得到有效证据。逐项核对，禁止批量勾选或按完成比例推断验收。
- 混合多项要求的检查项仅部分完成时保持未勾选，在旁边说明已交付与剩余范围；必要时拆成等价子项，保留全部原要求、阈值与失败路径。
- 契约、fake、组件测试、浏览器冒烟、真实引擎和目标拓扑验证各自只证明实际覆盖范围。单库、跳过、逻辑集群或合成媒体不得替代 AC 明确要求的双库、真实执行、物理拓扑或质量证据。
- 仅同步 issue 时优先复用已有有效证据；缺少证据就保留未验收，不扩成业务实现、模型加载或运行态变更。

保持恰好一个现有 `status:*` 标签，按实际剩余工作选择：

| 标签 | 使用条件 | GitHub state |
| --- | --- | --- |
| `status:planned` | 尚未开始，开工输入尚未齐备且未构成当前必须推进事项的实际阻塞 | `open` |
| `status:ready` | 具名开工输入已可用，尚未开始实施；不表示运行能力 ready | `open` |
| `status:in-progress` | 已实施部分步骤，仍有实现工作 | `open` |
| `status:integration` | 本范围实现已交付，仍需生产装配、消费者接入或联合联调 | `open` |
| `status:qualification` | 相应集成已完成，仍需行为、质量、故障恢复或目标拓扑资格验收 | `open` |
| `status:blocked` | 关键下一步确被缺失前置阻断；正文写明具体制品、负责人、影响和解除条件 | `open` |
| `status:done` | 完整范围、任务、全部 AC 与适用退出条件均有有效证据，未遗留本范围工作 | `closed` / `completed` |

这些状态不是自动递增流水线。合并后仍有实现项就继续 `in-progress`；只缺联调或资格时分别用 `integration`、`qualification`。部分路径等待依赖而其他工作仍可推进时，在正文说明，不把整包标为 `blocked`。远端缺少约定标签或使用了不同状态体系时报告差异，不擅自创建或重命名。

关闭与重开另行核对：

- 完整验收通过才关闭，并同步 `status:done`；本次交付完成使用 `completed`，不使用 `not_planned` 掩盖剩余工作。原有完成证据有效且本次未受影响时保留，不因本 PR 未覆盖它而取消勾选。
- 发现 closing keyword 自动关闭了未完成的相关 issue 时，先读最新正文、关闭事件和后续验收证据；确认误关且授权覆盖状态维护后，重开并恢复符合现状的标签。人工关闭、重复项、取消范围或原因不明时不自动重开，报告冲突并提交具体建议。
- 工作包按完整范围关闭；早期 Gate 只验该阶段的具名交付和前置，不要求所有关联工作包整包关闭。A01、A07/B07/C08 等持续交付包不能因早期 Gate 放行而提前关闭。
- Gate 逐项核对联合验收、上一 Gate 等明确前置和放行条件；Epic、总控分别核对自己的退出条件。更新受影响摘要与证据引用，子项关闭或单个 PR 合并不自动关闭父项。

## 3. 更新当前正文，控制内容增长

按 [AGENTS.md](../../../AGENTS.md) 维护四个独立部分，不追加平行的过程章节：

| 部分 | 合并后的更新 |
| --- | --- |
| `目标` | 保留原问题、完整交付范围与边界；合并不构成删减范围的理由 |
| `进展总结` | 替换过期现状，写清本 PR 已集成内容、关键证据、仍缺实现/接入/验证、风险与阻塞；链接合并 PR 和对应版本证据 |
| `任务清单` | 仅勾选有交付依据的具体步骤；保留未完成项，显式说明部分交付 |
| `验收标准（AC）` | 逐项保留行为、阈值、拓扑与失败路径；仅勾选有对应验收证据的条目 |

正文使用“已集成……”“已验证……”“尚未接入……”“完成……后验收”等直接语态，标明证据覆盖范围和核验日期（`Asia/Shanghai`）。合并日期与验证日期分别说明，避免把两者混同。

每次更新都维护一份当前版本，不积累合并日志：

- **就地替换。** 更新已有摘要与检查项，不按 PR、日期、轮次追加“最新进展”“本轮实施”等章节，也不把旧正文藏进折叠区。相同事实只在最合适的位置说明，其他位置保留必要引用。
- **任务归并。** 对齐原任务和 AC 更新，不为每个提交、修复尝试或测试运行新增一组检查项。已完成项保留简短结论和必要证据；未完成项保留完整要求。独立工作持续扩大时给出拆分建议，不自行创建子 issue 或缩减原范围。
- **证据收敛。** 同一结论优先引用当前有效的 PR、报告或证据索引，不逐条累加重复链接、命令输出、测试数字与 SHA。移除已有可靠出处且被替代的过程描述；唯一验收依据尚无可靠外链时保留最小摘要，不因压缩丢失可追溯性。当前失败、未决问题和阻塞不得被成功摘要吞没。
- **长度预算。** 进展总结通常 3–5 条，默认不超过 600 字符；完整正文默认不超过 6000 字符，统计包含 Markdown、链接和折叠区。预算用于触发压缩，不允许截断正文、删除 AC、降低阈值或省略失败路径来达标。
- **增长检查。** 写前比较新旧正文字符数；超出预算或较旧正文增长超过 10% 时，先去重、合并和收敛证据。没有新增的已授权范围或影响实施/验收的必要事实时，更新后原则上不长于更新前；原正文已超预算时优先压缩。完整保留要求后仍须超出时，在最终交付说明长度与必要原因，不把这些统计写入 issue。
- **不转移堆积。** 详细日志、逐轮尝试、截图和完整测试明细链接到已有 PR 或验证报告；不为每次合并追加长评论或重复报告。无新事实时不写入，不暴露凭据、私人内容或内部运行路径。

父项只汇总本层成果、退出条件和子项链接；依赖方只在所需接口、版本或制品确实可用时更新相应前置。生产者 PR 合并不表示消费者已接入，也不自动解除整包阻塞。

## 4. 写入、回读与重试

1. 写入前明确每张 issue 拟改的正文片段、任务/AC、state 和唯一状态标签，并执行第 3 节的长度与增长检查。仅正文更新模式保持状态与元数据不变；完整同步模式按已核对结果执行，沿用已有授权。
2. 每次写前即时重读正文、状态、标签与更新时间，和用于判断的版本比较。保留其他人的新内容；同段改动意图不明时暂停该 issue 的写入，继续其他独立项。能安全合并时刷新后重算一次，仍有冲突则报告，禁止用旧全文覆盖。
3. 只修改计划内字段，保留标题、非状态标签、负责人、里程碑、优先级、Projects 字段和原生关系。若接口要求完整标签集合，基于最新读取值仅替换 `status:*`。只有授权包含 Projects 状态维护且已读取该项目真实字段/选项时才同步，不凭名称猜 ID。
4. 优先使用结构化更新参数；使用 `gh` 写多行正文时，把精确文本写入临时 UTF-8 文件并传 `--body-file`，不把 issue 内容拼入 shell。接口允许时一次提交该 issue 的相关字段；需分步时先写证据正文，关闭动作最后执行。
5. 每张写后回读，核对四部分内容、勾选与证据、长度、state/关闭原因、唯一状态标签及未授权字段是否保持；确认压缩没有遗漏原有要求、未决问题和唯一证据。写入超时或结果未知时先查现状，再补缺失步骤，不盲目重放。权限错误或持续冲突时停止该项，不宣称同步成功。
6. 重复执行同一 PR 时先比较当前有效事实与目标；无变化就不写入，不为更新时间、重复链接或进度评论制造噪音。

## 5. 刷新跟踪快照并交付

涉及编排清单内的 issue 时，远端回读通过后，从仓库根目录刷新本地矩阵：

```bash
python3 scripts/dev-env/refresh-implementation-tracker.py
```

先检查目标文件已有 diff。存在他人或来源不明的改动时，使用 `--output <临时文件路径>` 生成并核对，不覆盖现有文件。刷新工具只读取 GitHub、生成本地快照，不能证明 AC 通过；不要把 `--root-body` 输出直接覆盖总控的四部分正文。刷新失败时报告快照未更新，不回退已核实的远端结果。不因刷新自动 commit、push 或创建新 PR。

最终简要给出 PR 合并依据，以及每张相关 issue 的链接、state/标签变化、正文和任务/AC 变化、剩余工作。区分“写后已回读”“无需变更”“未写入/失败”；没有确认相关 issue 时说明检索范围，不虚构关联。仅演练时明确所有改动均为建议。
